# AI Agent 越用越乱？先把工作边界划清 讲清 Agent 的四层工作边界，并且分享我的常驻Skill。 部分动画画面由AI生成。

## 精华版
作者长期使用后只保留两个常驻自动化能力：一个在需要换对话时提醒并整理交接，一个把资料搜集、调研、长文分析、反复对比等重任务分流到网页端，只回传结论。核心结论是：用久后最容易出问题的是工作边界，不是模型能力。四层边界分别是：长期项目固定文件夹，沉淀规则、工具和经验；同一任务及时换对话并交接，避免历史被反复压缩后失真；独立重任务隔离处理，只回传结论；多方案并行改同一项目时各用独立副本，跑通再合并。最终形成流水线：固定环境→及时交接→任务分流→并行隔离→合并。

## 整体逻辑链条梳理
1. 长期工作先固定规则与工具 → 因为新对话需要低成本接手，项目经验必须可复用；这引出“固定环境”边界。
2. 同一任务及时切换并交接 → 因为对话越长越依赖压缩，多轮压缩会丢细节；这引出“会话长度”边界。
3. 独立重任务分流 → 因为资料搜集、调研、长文分析等会占用主流程容量，隔离后只回传结论；这引出“任务上下文隔离”边界。
4. 多方案并行时隔离文件修改 → 因为多个执行者改同一项目目录会覆盖、干扰，隔离后合并；这引出“文件修改隔离”边界。
5. 四层边界组合成流水线 → 前四层分别解决环境、会话、任务、文件四类边界，按“固定环境→及时交接→任务分流→并行隔离→合并”衔接。

## 技术名词快速上手讲解
- **Agent（智能体）**
  - 一句话本质：能接收指令、调用工具、执行多步任务并产出结果的软件系统。
  - 结构化拆解：由指令与规则、工具或文件访问能力、执行循环、结果输出等部分组成；工作时读取目标与规则，规划步骤，调用工具，根据结果继续或结束。
  - 作用定位：本文讨论的对象；工作边界管理决定它能否长期稳定使用。

- **Skill（含常驻 Skill、交接 Skill、网页替身）**
  - 一句话本质：把特定场景的任务说明、操作流程和工具调用封装成可复用能力，让 Agent 按固定方式执行。
  - 结构化拆解：通常包含触发条件、步骤与规则、工具或脚本调用、输出与交接方式；常驻后可在需要时被识别并执行，减少重复交代。文中两个常驻 Skill：交接 Skill 负责提醒换对话并整理交接；网页替身负责把重任务分流到网页端并回传结论。
  - 作用定位：作者用两个常驻 Skill 管理“对话交接”和“任务分流”两类边界。

- **token**
  - 一句话本质：AI 系统处理文字时使用的计量单位，也是成本与容量占用的度量。
  - 结构化拆解：包括输入与输出计量；受上下文窗口上限影响；用量影响成本，也影响是否需要压缩历史。
  - 作用定位：解释为什么子 Agent 会拖 token、为什么要把重任务分流到网页端。

- **项目文件夹**
  - 一句话本质：为一段长期工作固定规则、工具、资料和记录的工作目录。
  - 结构化拆解：包含规则文件、脚本与依赖、素材记录、可复用环境；新对话进入后读取这些内容即可接手。
  - 作用定位：第一层边界，解决长期工作的经验沉淀和环境复用。

- **AGENTS.md**
  - 一句话本质：放在项目中的规则说明文件，供 Agent 读取并遵守。
  - 结构化拆解：可写规范、流程、约定和记录；新会话读取后直接按规则执行。
  - 作用定位：项目文件夹沉淀经验的典型载体，文中用于视频分割规范、字幕规范、素材记录等。

- **上下文与自动压缩**
  - 一句话本质：上下文是 AI 系统当前可见的对话与资料；自动压缩是超出窗口时对历史做摘要以继续。
  - 结构化拆解：上下文有窗口上限；压缩会触发摘要；多轮压缩会累积细节丢失。
  - 作用定位：解释为什么同一件事不能在一个对话里拖太长，以及为什么需要及时交接。

- **子 Agent**
  - 一句话本质：由主 Agent 派生、在独立上下文中执行子任务的 Agent。
  - 结构化拆解：包含主任务、子任务、独立上下文、结果回传；子任务在外部分析，只把提炼结论带回主工程。
  - 作用定位：第三层边界的思路来源，核心价值是上下文隔离。

- **Codex 与 ChatGPT 网页端**
  - 一句话本质：两个独立用量与独立上下文的 AI 使用端，官方客户端提供两端连接通道。
  - 结构化拆解：Codex 侧承担主工程；网页端侧在独立上下文中分析；两端用量分开、不公用；通过连接通道回传结论。
  - 作用定位：网页替身 Skill 的基础机制。

- **Worktree**
  - 一句话本质：在同一项目代码目录下创建多个独立工作目录，让不同方案并行修改而不互相覆盖。
  - 结构化拆解：包含原项目、独立工作目录、各自修改、最后合并；每个执行者改自己的副本。
  - 作用定位：第四层边界，用于多对话、多方案同时改一个项目时隔离文件修改。

## 一句话结论
对应链条第5环：Agent 用久后真正容易出问题的是工作边界不清，应按项目文件夹、对话交接、子任务隔离、Worktree 四层划清边界，并把它们串成固定环境→及时交接→任务分流→并行隔离→合并的流水线。

## 核心要点
对应链条第1-5环：
- 对应链条第1环：长期项目应建项目文件夹，沉淀规则、工具和经验，让新对话直接接手。
- 对应链条第2环：同一任务不宜无限拖长，应在需要时换对话并自动整理交接，避免多轮压缩后失真。
- 对应链条第3环：资料搜集、调研、长文分析、反复对比等独立重任务应隔离处理，只把结论带回主工程。
- 对应链条第4环：多对话多方案同时改同一项目时才用 Worktree，各改各的，跑通再合并。
- 对应链条第5环：四层边界组合成流水线：固定项目环境→及时交接→任务分流→并行隔离→合并。

## 关键细节
对应链条第1-4环：
- 作者称烧了40多亿 token 后，常驻 Skill 只有两个：一个提醒交接，一个把杂活丢出去省 token。
- 项目文件夹例子：AGENTS.md 写视频分割规范、字幕规范、素材记录；任务生成项目、视频素材处理脚本、依赖配置放在项目内，新对话进来即可直接干活。
- 对话边界：100万上下文被说成标配，但自动压缩前一兩轮还好，多压几轮会“面目全非”，后面任务出错概率直线上升。
- 交接 Skill：在需要交接时主动提醒换对话；确认后自动整理干完了什么、敲定了什么规矩、下一步从哪里开始，并自动开新对话发送相关指令。
- 子 Agent 核心价值是上下文隔离；现实干活中作者少用，主要因为太拖 token。
- 网页替身：ChatGPT 网页端和 Codex 端用量完全分开、不公用，官方客户端自带两端连接通道；重任务自动交网页端，在独立上下文中分析，跑完回传提炼结论；主要针对 Codex 编写，其他 Agent 可自行修改。
- Worktree：多个对话改同一项目文件夹容易互相覆盖、干扰；Worktree 给每个对话单独复制一份项目，各改各的，最后合并最好结果；单对话顺序干活没必要开，多对话多方案同时改一个 Codex 项目时再用。

## 原文文案

烧了40多亿 token 后，我现在常驻的 Skill 就两个。一个提醒我什么时候该换对话做交接，另一个把杂活丢出去帮我省 token。看起来解决的是两个不同的问题，但它们其实都指向同一件事：Agent 的工作边界。Agent 用久了之后，我发现最容易出问题的，其实不是模型能力，而是工作边界没划清楚。一个对话到底该用多久，什么时候开新项目，什么活适合丢给子 Agent，什么时候需要我合入。这期就把这四层边界一次性讲清楚，欢迎来到桌子的频道。我帮很多新手配置 Agent 的时候，他们经常问我一个问题：既然已经给了 Agent 完全访问权限，它哪里都能去，那为什么还要推荐一个项目文件夹呢？如果只是做一个短任务、一次性任务，或者闲聊，那确实没有必要，但当你真正做一系列事情或者一个完整项目的时候，文件夹的重要性就出来了。打个比方，你有整栋楼的门禁卡，不代表你不需要一个固定的办公室，完全访问解决的是它能不能去，而项目文件夹解决的是这件长期工作有没有固定的规则和工具，它最重要的意义就是帮这段工作搞定两件事。第一件事，沉淀项目经验，比如我的 AGENTS.md 里，视频分割规范、字幕规范、素材记录，写在项目文件夹里，换任何新对话进来，Agent 读一遍这些文件就能直接上手；第二件事固定工作环境，比如我的任务生成项目，以及视频素材处理脚本、依赖配置全在里面，下次开新对话进来，不是一片毛坯房，而是工具全摆在桌上，直接拿起来就能开始干活。项目文件夹有了以后，第二个就是对话。如果项目文件夹是办公室，那对话就是今天摆在桌面上的工单。大家都知道不同的活最好分开了，但是容易忽略的一点是，同一件事也别在一个对话里拖得太长。很多人觉得现在模型足够聪明，支持100万上下文都是标配，而且上下文长了 Agent 会自动压缩，实际上经常用的就知道，自动压缩上下文前一两轮还好，多压几轮就压得面目全非了，后面任务出错概率直线上升。所以与其让一个对话反复压、硬撑下去，不如及时做好交接。但是有两个很烦的地方：一是我不是一直想着交接这个事情，有时候跟 AI 聊嗨了根本没想到这一茬，等做事情开始漂移了才反应过来；二是直接换新对话，它根本不知道你前面干了什么，你又得当打字员重新交代一遍。所以我常驻的这个交接 Skill 给我，在需要做交接的时候主动提醒我换对话，防止我聊过头，然后我确认交接后自动帮我把干完了什么、敲定了什么规矩、下一步从哪里开始整理好，并且自己帮我开一个新对话发送相关指令，直接无缝接着开，这样既不用当打字员，也不用操心什么时候该换对话。接下来是最容易被神话的一个：子 Agent。很多人看到多 Agent 觉得很酷炫，但现实干活中我很少会用到，为啥呢？不是说子 Agent 的不好用，主要是因为太拖 token 了，但是子 Agent 的思路很值得借鉴。子 Agent 最核心的价值其实就四个字：上下文隔离。派小弟去外面翻五万字的垃圾资料，把脏活杂活留在外面，最后只把提炼好的结论带回主工程。于是我沿用子 Agent 的思路，做了第二个常驻 Skill，我管它叫网页替身。我们都知道 ChatGPT 网页端和 Codex 端用量是完全分开、不公用的，而且官方客户端自带了两端的连接通道，于是我就利用这个机制做了一套自动化分流。凡是遇到资料搜集、调研、长文分析、反复对比这种又重又吃推理的独立子任务，会自动交给网页端跑，网页端在它自己独立的上下文里分析推理，跑完把提炼的结论带回来给 Codex。这个 Skill 主要针对 Codex 来写，你如果用的是别的 Agent 也一样，这个 Skill 你自己去改。最后一个就是 Worktree。前面几个不同对话只是把任务上下文分开了，可如果这几个对话最后都去改同一个项目文件夹里的文件，还是很容易互相覆盖、互相干扰。Worktree 就相当于你给每个对话单独复制一份项目，让它们各改各的，最后把最好的结果合并回来。所以如果只是一个对话按顺序干活，完全没有必要开；多个对话、多个方案同时改一个 Codex 项目时再用 Worktree。最后我们把这四个边界放回一个完整的流水线：开一系列长期活，就建项目文件夹，把规则、工具放进固定办公室；推进不同任务就换对话，同一个事情做得太长太久了也要及时做好交接；查资料、重度分析，别硬塞给 Agent，把活派给网页端，最后只把提炼好的结论带回主工程；多方案并行的时候开 Worktree，让每一个独立沙盒，跑通了再合并。Agent 用久了，真正容易出问题的往往不是模型不够强，而是什么活都往同一个地方塞，把边界画清楚，Agent 才会越用越顺。
