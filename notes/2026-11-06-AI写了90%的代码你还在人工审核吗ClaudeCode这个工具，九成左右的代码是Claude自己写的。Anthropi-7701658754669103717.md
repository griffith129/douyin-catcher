# 精华版

该编程助手仓库约九成代码由机器生成；公司每日改动从 5 月两千多个增至 9 月三万多个。6—9 月合入改动翻倍多，线上撤回比例降四成多。做法不是取消检查，而是边写边查，机器承担大部分逐行读码，人按风险批准并最终负责；一个改动要过七道关卡：本地自检并用干净状态重审、多个机器审查并投票、独立安全扫描、几十项自动检查、按风险 0/1/2 人批准且机器批准不算、合并前在最新代码上复测并用隐藏开关先给员工用、线上快速监控与撤回。期间出现写码机器与审查机器互斗，一个改动一夜改 50 多轮；约 59% 被反复挑的是第一轮就存在的旧代码。四条规则——最多 3 轮、只看新改动、同类一次改完、提过不再提——使一次通过率 65% 升至 78%，5 轮以上从近 9% 降至 1.5%。人负责需求取舍、高危代码、核心结构、看证据、每个上线改动负责到底；事故和紧急撤回做成考题，检查规则、工具或底层机器改动先跑考题；按需让编程助手讲解当前代码；改动拆小、快速撤回、谁合谁负责。

## 整体逻辑链条梳理

1. 写码效率提高 → 每日改动量激增 → 审查成为瓶颈；因此不能只靠发布前人工逐行看。
2. 把检查前移到写码过程，机器承担大部分读码，人只处理关键点；因此需要可自动执行的多道关卡。
3. 七道关卡按“本地自检 → 联合审查 → 安全扫描 → 自动检查 → 风险批准 → 合并复测与功能隐藏 → 线上监控回滚”排列；每道减少前道剩余风险，形成兜底。
4. 机器审查规模化后出现写审互斗与重复挑旧代码；因此用四条规则约束轮次、范围、同类修复和去重，提升一次通过率。
5. 机器接管读码后，人聚焦需求取舍、高危代码、核心结构、证据审阅与最终责任；责任闭环保证速度不牺牲可追责性。
6. 审查器本身会退化；把事故和回滚做成固定考题，改规则、工具或底层模型前先评测，形成持续迭代闭环。
7. 机器读码带来工程师熟悉代码库问题；用按需讲解、拆小改动、快速撤回和谁合谁负责，兼顾理解与安全。

## 关键概念首现讲解

### Claude Code、Agent、模型、AI、上下文

1. **一句话本质**：Claude Code 是本文中的编程工具，Agent 是能自主执行任务的程序，模型是生成判断的计算系统，AI 是让机器完成认知任务的技术总称，上下文是模型当前可见的信息。
2. **结构化拆解**：
   - Claude Code：围绕代码生成、修改、检查执行开发任务的工具。
   - Agent：接收任务、调用工具、循环执行直到完成的程序；本文区分“写代码的 Agent”和“审查代码的 Agent”。
   - 模型：根据输入生成内容或判断的计算系统；本文中用于写码、审查、判断风险等级。
   - AI：让机器完成通常需要人类认知任务的技术总称。
   - 上下文：模型在当前任务中可见的信息；全新上下文指不带旧对话干扰重新审查。
3. **作用定位**：这些概念支撑全文主线：机器写码、机器审查、人工最终负责。

### PR、bug

1. **一句话本质**：PR 是把一处代码改动提交给团队审查并合入的请求，bug 是代码缺陷。
2. **结构化拆解**：
   - PR 包含改动内容、目标代码、审查记录和检查结果。
   - 提交 PR 后会触发自动检查、机器审查和人工批准。
   - 未处理完的审查意见会阻止合入。
   - bug 是代码行为与预期不符的问题。
3. **作用定位**：七道关卡围绕 PR 展开，bug 是机器联合审查要发现的主要对象。

### 测试、构建、lint

1. **一句话本质**：测试、构建、lint 是三类本地自动检查。
2. **结构化拆解**：
   - 测试：运行用例验证代码行为。
   - 构建：把源码生成可运行产物。
   - lint：按规则检查代码格式与常见错误。
3. **作用定位**：它们是第一道关卡，让写码 Agent 在提交 PR 前先自证可运行。

### Review.md

1. **一句话本质**：Review.md 是放在关键目录里的审查提示文件。
2. **结构化拆解**：
   - 位置在关键目录下。
   - 内容写明该区域最容易踩坑的地方。
   - 审查 Agent 读取后用于前置领域经验。
3. **作用定位**：把历史经验变成机器审查可读取的提示，减少重复踩坑。

### 联合审查、投票、Important/Nit 标签

1. **一句话本质**：联合审查是多个审查 Agent 并行找问题，再由另一组 Agent 投票确认；Important 是重要问题标签，Nit 是小问题标签。
2. **结构化拆解**：
   - 多个 Agent 同时找 bug。
   - 另一组 Agent 投票，足够多 Agent 认可才发出意见。
   - 纯风格问题和顺手意见会被丢弃。
   - 意见打上 Important、Nit、旧代码三类标签。
3. **作用定位**：第二道关卡，用投票阈值过滤噪声，提高实质修改意见比例。

### 安全审计、凭证泄漏

1. **一句话本质**：安全审计是用专门规则扫描安全漏洞和密钥暴露。
2. **结构化拆解**：
   - 使用独立规则库。
   - 扫描代码改动中的安全漏洞。
   - 扫描凭证泄漏，凭证包括密钥、账号等敏感信息。
3. **作用定位**：第三道关卡，独立于普通 bug 审查，专门兜底安全风险。

### 自动化检查：格式、类型检查、跨平台测试、全量构建

1. **一句话本质**：自动化检查是在人工看之前跑完的一整套机器检查。
2. **结构化拆解**：
   - 格式检查：检查代码格式是否符合规则。
   - 类型检查：检查数据用法是否符合类型约定。
   - 跨平台测试：在不同系统环境运行测试。
   - 全量构建：完整构建所有目标。
3. **作用定位**：第四道关卡，普通 PR 真人未看前先跑几十项检查。

### 风险分级批准

1. **一句话本质**：风险分级批准是按改动风险决定需要几名真人批准。
2. **结构化拆解**：
   - 专门模型看代码内容判定风险等级。
   - 文档、文案低风险：自动检查全绿可直接合入，0 人批准。
   - 普通业务或自动更新等敏感处：1 名工程师批准。
   - 最高风险：2 人一起批准。
   - 机器批准不算数；提交新改动后旧人工批准作废。
3. **作用定位**：第五道关卡，把人工注意力集中到高风险改动。

### 合并队列、main 分支、功能开关、回滚

1. **一句话本质**：这是一组控制改动合入和发布暴露范围的机制。
2. **结构化拆解**：
   - 合并队列：改动合入前排队，并在最新 main 分支上完整重跑检查。
   - main 分支：团队最新主干代码。
   - 功能开关：配置项控制新功能是否对用户可见；先给员工用，再分批放量。
   - 回滚：发现问题后快速撤回改动。
3. **作用定位**：第六、七道关卡，防止两个各自能通过的改动合到一起搞坏主干，并控制线上事故影响。

### git blame

1. **一句话本质**：git blame 是逐行查看代码最后修改记录的工具。
2. **结构化拆解**：
   - 定位某行代码来自哪次提交。
   - 查看修改者和修改时间。
   - 本文用它发现被反复挑刺的代码多为第一轮就存在的旧代码。
3. **作用定位**：诊断写审互斗，判断审查 Agent 是否在反复深挖历史旧问题。

### 评测集、提示词、CI 配置、diff

1. **一句话本质**：这是审查器持续迭代用的固定考题和输入材料。
2. **结构化拆解**：
   - 评测集：把每次线上事故和紧急回滚做成固定考题。
   - 提示词：给审查 Agent 的审查指令。
   - CI 配置：自动构建与检查的配置文件。
   - diff：代码差异。
3. **作用定位**：改提示词、工具或底层模型前先跑评测集，抓 bug 分数涨才保留，掉则撤回。

## 一句话结论

对应链条第 1—7 环总览：该团队在 Claude Code 仓库约九成代码由机器生成、日改动量从 5 月两千余增至 9 月三万余的背景下，用“边写边查、七道机器与人工关卡、人工最终负责”的流程，使 6—9 月合入改动翻倍多、撤回比例降四成多。

## 核心要点

对应链条第 1—7 环。

1. 写码效率提升造成审查瓶颈，团队把审查从发布前集中检查改为边写边查，大部分读码交给机器（对应链条第 1—2 环）。
2. 一个改动要过七道关卡：本地自检与重审、联合审查、安全审计、自动化检查、风险分级人工批准、合并队列与功能开关、线上监控回滚（对应链条第 3 环）。
3. 机器审查规模化后出现写审互斗和反复挑旧代码，团队用“最多三轮、只看新改动、同类一次改完、提过不再提”四条规则，使一次通过率从 65% 升至 78%（对应链条第 4 环）。
4. 人负责需求取舍、高危代码、核心结构、证据审阅，并对每个上线改动负责到底（对应链条第 5 环）。
5. 审查器用线上事故和紧急回滚做评测题，提示词、工具或底层模型改动先跑评测，分数涨才保留（对应链条第 6 环）。
6. 机器读码后，工程师按需让 Claude Code 讲解当前业务逻辑来熟悉代码库；改动拆小、快速撤回、谁合谁负责（对应链条第 7 环）。

## 关键细节

对应链条第 3—7 环，以下事实值得记住。

- 6 月到 9 月，合入的改动翻了一倍多，被撤回的比例反而降了四成多。
- 5 月全公司每天合入两千多个代码改动，9 月涨到三万多个；Claude Code 仓库约九成代码由 Claude 自己写。
- 第一道关卡：开 PR 前，Claude 在本地跑测试、构建、lint，再调起一个全新上下文的 Agent 重审；关键目录放 Review.md 写明易踩坑点；Boris Cherny 估计这让输出代码质量好两到三倍。
- 第二道关卡：提 PR 后多个 Agent 同时找 bug，另一组 Agent 投票，足够多 Agent 认可才发意见；纯风格和顺手意见丢弃；意见标签为 Important、Nit、旧代码；旧代码历史包袱不算当前作者；内部 PR 收到实质修改意见的比例从 16% 升到 54%。
- 第三道关卡：独立安全审计，用专门规则扫描安全漏洞和凭证泄漏。
- 第四道关卡：代码格式、类型检查、跨平台测试、全量构建等全套自动化检查；普通 PR 真人未看前先跑几十项检查；未处理完审查意见不能合入，作者要么修掉，要么写清理由手动关闭。
- 第五道关卡：改文档、文案等低风险改动，自动检查全绿可直接合入；普通业务改动或自动更新等敏感处要 1 名工程师批准；最高风险代码必须 2 人一起批准；风险等级由专门模型看代码内容判定；机器批准不算数；提交新改动后旧人工批准作废。
- 第六道关卡：进入合并队列，合入主干前先拉到最新 main 上完整重跑检查，防止两个各自能通过的改动合到一起搞坏主干；新功能用功能开关藏起来，员工先用，确认稳妥再分批放给所有用户。
- 第七道关卡：线上快速监控与快速回滚；团队算过账，放慢节奏能少踩坑但干的事也变少，所以选择把发现问题和修复问题练到极快。
- 坑：写代码的 Agent 和审查代码的 Agent 会互相较劲，有个 PR 一夜来回改 50 多轮，最后作者手动叫停；用 git blame 查得被反复挑刺的代码里约 59% 第一轮就在仓库里，审查 Agent 每轮都在深挖旧问题。
- 四条规矩：审查最多跑 3 轮，3 轮不过作者必须停下重想方案；后续轮次只看新增改动；发现一类 bug 要求同类全改；提过的问题后续不再提。
- 四条规矩效果：一轮直接通过率从 65% 升到 78%；折腾到 5 轮以上的极端情况从接近 9% 降到 1.5%。
- 审查器迭代：每次线上事故和紧急回滚做成评测集里的一道考题；每次改提示词、工具或底层模型，都在评测集重跑；抓 bug 分数涨才保留，掉立刻撤回；每天自动跑评测。
- 工程师职责：源头决定需求该不该做；亲自把关计费逻辑、CI 配置、自动更新等高危代码；盯会被其他部分照抄的核心代码结构；看测试输出、运行截图和审查日志；任何合入上线的改动必须有具体的人负责到底。
- 熟悉代码库：要改哪块业务，就让 Claude 现场讲解那一块，花三五分钟讲系统当前实际逻辑；比每天强迫自己逐行看所有 diff 学到更多。
- 铁律：谁合进去的代码谁负责到底；每个改动拆得很小，出岔子几分钟内就能彻底撤回。

## 原文没有讲清的问题

对应逻辑链开放问题，主要落在第 3、4、5、6、7 环。

- 机器审查漏掉的问题比例、误报比例如何持续度量？评测集只来自已发生的事故和回滚，是否覆盖尚未暴露的风险？

## 原文文案

Claude Code 仓库里有九成左右的代码是 Claude 自己写的。整个公司每天的代码改动量从五月的两千多个暴涨到九月的三万多。写代码的速度上去了，那谁来审核呢？Anthropic 在官网上发布一篇文章，公开了他们内部的审查办法。从今年六月到九月，Claude Code 合进去的代码改动翻了一倍多。线上代码被撤回的比例反而降了四成多。他们继续严格做代码审查，只是换了一种思路。大部分读代码的繁重体力活直接交给了机器。以前是这段代码有没有真人逐行看过，有没有发现错误。现在重点是，这个改动可能出什么错，该交给哪道检查来兜底。审查不再堆在发布前的最后关头，变成了边写边查，跟拼写检查一个道理。大部分改动最多一个人参与，同时撤回率和事故率还不能涨。一个改动从写完到上线要连过七道关卡。第一道关卡，在提 PR 之前，Claude 在本地写完代码，先自己把测试、构建和 lint 全跑通。接着再调起一个全新上下文的 Agent，把这次的代码变动重新审一遍。Claude Code 作者 Boris Cherny 估计，这种方式让 Claude 能自己验证，输出代码的质量就能好两到三倍。而且关键目录下还会放一份 Review.md，专门写清楚这块代码最容易在什么地方踩坑。第二道关卡，提了 PR 之后，先过一轮 AI 的联合审查。系统会派出多个 Agent，同时找 bug，再由另一组 Agent 投票。只有足够多的 Agent 都认定是真问题才会发出来，单纯挑代码风格和顺手提的意见，系统会直接丢掉。审查意见打上三种标签：Important、Nit，还有原本就存在的旧代码。老代码里的历史包袱绝不算在当前作者头上。这套机制跑起来之后，收到实质性修改意见的内部 PR 从 16% 一下子涨到了 54%。第三道关卡是独立的安全审计，用专门规则扫描安全漏洞和凭证泄漏。第四道关卡是全套的自动化检查，代码格式、类型检查、跨平台测试、全量构建，一个都不能少。一个普通的 PR，真人还没看，机器就已经跑完了几十项检查。只要还有没处理完的审查意见，改动就合不进去，作者要么修掉，要么写清楚理由手动关闭。第五道关卡，看改动的风险级别，决定要几个人签字批准。改文档、改文案这种低风险改动，只要前面的自动化检查全绿就能直接合入。普通的业务改动，或者自动更新这种敏感地方，要一个工程师批准。最高风险的代码，必须两个人一起批准。改动属于哪个风险等级，由专门的模型看代码内容来定。不管这行代码是谁写的，机器给的通过，顶替不了真人。只要提交了新改动，之前的人工批准直接作废，必须重新批。第六道关卡是进入合并队列。改动合入主干前，先拉到最新的 main 分支之上，把所有检查完整再跑一遍。防的是两个各自能通过的改动，合到一起把主干搞坏。新功能合进去之后，先用功能开关藏起来，员工自己先用。确认稳妥了，再分批放给所有用户。第七道关卡是线上的快速监控与快速回滚。团队里有人算过一笔账，放慢节奏确实能少踩坑，但主要是因为干的事情也变少了。所以他们选择把发现问题、修复问题的速度练到极快。这套流程刚跑起来的时候，碰上过一个很尴尬的问题。写代码的 Agent 和审查代码的 Agent 会卡在死循环里互相较劲。有个 PR 在夜里来回改了 50 多轮，最后只能由作者手动叫停。团队后来用 git blame 顺着代码行一查。被反复挑刺的代码里，差不多 59% 从第一轮开始就一直躺在仓库里了。审查 Agent 根本没找到什么新问题，只是每一轮都在深挖历史代码里的旧问题。发现这个毛病之后，他们立了 4 条规矩。第一条，审查最多跑 3 轮，3 轮还不过，作者必须停下来重新想方案。第二条，后面几轮审查只看新增的改动，不许回头翻旧账。第三条，发现某一类 bug 就要求作者把同类的全改掉。第四条，已经提过的问题，后续轮次绝不再提。规矩改完之后，一轮直接通过的 PR 从 65% 上升到了 78%，折腾到 5 轮以上的极端情况，直接从接近 9% 降到了 1.5%。那审查 Agent 自身平时怎么迭代。他们把每一次线上事故和紧急回滚都做成了评测集里的一道考题。团队每次改动审查用的提示词、工具或者底层模型，都要在这套评测集上重新跑一遍。抓 bug 的分数涨了才保留，分数掉了立刻撤回，每天都在自动跑评测。机器把读代码的体力活包圆了，那工程师平时干什么？主要抓这几件事：第一，在源头上决定这个需求到底该不该做。第二，亲自把关计费逻辑、CI 配置、自动更新这类高危代码。第三，盯紧那些会被其他模块当成模板照抄的核心架构。第四，看证据，重点看测试输出、运行截图和审查日志，还有一点最重要，任何一个合入上线的改动都必须有一个具体的人负责到底。还有一个实际问题，代码全让机器读了，工程师怎么熟悉代码库。他们的做法是，要改哪块业务，就让 Claude 现场讲解那一块。花上三五分钟，讲的还是系统当前的实际逻辑。这比以前每天强迫自己逐行看所有的 diff，学到的要多得多。他们团队有条铁律，谁合进去的代码，谁负责到底。每个改动都被拆得很小，万一出了岔子，几分钟内就能彻底撤回。
