# A2A协议详解：AI智能体如何发现、认证并协作？学习笔记

## 精华版

**A2A协议（Agent-to-Agent protocol）**  
- **一句话本质**：它是为AI智能体之间互相发现、认证和通信而定义的标准协议。  
- **结构化拆解**：  
  - 解决三类问题：跨智能体协作、认证要求、通用通信方式；  
  - 工作机制分三阶段：发现、认证授权、通信；  
  - 通信既支持普通请求响应，也支持长任务的流式状态更新。  
- **作用定位**：本文主题。它让不同来源的智能体不必为每一次集成都写自定义代码，而能按统一规则协作。

**AI智能体（AI agent）**  
- **一句话本质**：能感知环境、做决策并采取行动以实现目标的自主系统。  
- **结构化拆解**：  
  - 组成/问题：感知、决策、行动、目标；  
  - 关键机制：感知环境→依据目标决策→执行动作→服务目标。  
- **作用定位**：A2A的参与主体。理解它才能理解为什么单智能体能力有限、为什么需要智能体间通信标准。

**主线浓缩**：单智能体难以独立完成复杂任务，跨组织使用他人智能体又缺少统一通信方式，因此需要A2A。A2A用公开描述完成发现，用安全方案完成认证授权，用标准消息格式完成通信，并支持长任务状态更新。它由Google于2025年4月提出，现由Linux Foundation托管开源；收益是标准化协作、隐私保护和易采用，但协议仍处早期，安全、治理、性能有待完善。

## 整体逻辑链条梳理

1. **问题起点**：AI智能体是自主系统，但复杂任务需要多个智能体协作；若使用他人的智能体，又不知道其通信方式。  
   - 为什么成立：旅行规划等任务需要旅行、航班、酒店、游览等多个智能体配合。  
   - 如何衔接：自定义集成成本高，于是需要标准协议。

2. **方案出现**：A2A协议被设计为智能体间协作标准，覆盖协作、认证和通用通信。  
   - 为什么成立：它同时处理“如何找到对方”“如何建立信任”“如何交换消息”。  
   - 如何衔接：要理解协议，先看参与角色。

3. **核心角色**：用户发起目标，发起方智能体代表用户请求其他智能体，执行方智能体接收并执行任务；同一智能体可在不同场景切换角色。  
   - 为什么成立：请求方与服务方的分工是协作的基本结构。  
   - 如何衔接：角色明确后进入三阶段流程。

4. **发现阶段**：执行方智能体公开描述自身身份、能力、技能、服务端点和认证要求，发起方据此找到并判断如何连接。  
   - 为什么成立：不知道对方能力和入口就无法发起有效请求。  
   - 如何衔接：知道入口和认证要求后，才能认证。

5. **认证授权阶段**：按公开描述中的安全方案认证，认证成功后由执行方负责授权和访问控制。  
   - 为什么成立：跨智能体协作需要先确认身份，再决定权限。  
   - 如何衔接：信任建立后才能通信。

6. **通信阶段**：发起方用标准消息格式发送任务，执行方可请求补充信息，完成后返回消息和生成物；长任务可流式推送状态。  
   - 为什么成立：统一消息格式和传输方式使不同实现可互操作。  
   - 如何衔接：机制成立后，收益与边界自然显现。

7. **收益与边界**：A2A带来标准化发现/认证/通信、隐私保护和基于既有标准的易采用性，但仍是早期协议。  
   - 为什么成立：收益来自标准化和黑箱协作；边界来自安全、治理、性能尚未成熟。  
   - 如何衔接：这些边界构成后文开放问题。

## 一句话结论

对应链条第2-7环：A2A通过公开描述完成发现、按安全方案完成认证授权、用标准消息格式通信，让不同AI智能体在不暴露内部实现的情况下协作完成任务。

## 核心要点

对应链条第2-7环：以下要点概括A2A从问题、机制到收益边界的主线。

- A2A是Google于2025年4月提出、现由Linux Foundation托管开源的智能体间协作标准。
- 它要解决复杂任务中多个智能体如何跨来源协作、认证和通信的问题。
- 核心流程分三阶段：发现、认证授权、通信。
- 发现依赖执行方公开自身身份、能力、技能、服务端点和认证要求。
- 通信使用标准消息格式，支持请求响应、补充信息、结果生成物和长任务状态更新。
- 收益包括标准化协作、隐私保护和基于既有标准易采用，但协议仍处早期，安全、治理、性能待完善。

## 关键细节

对应链条第3-7环：以下细节按角色、发现、认证、通信、长任务、隐私和标准采用展开。

- **核心角色与场景**：用户可以是人类操作员或自动服务，负责发起请求或设定目标；client agent 代表用户向其他智能体发起请求；remote agent 接收请求并执行任务。同一智能体在不同场景中可能作为发起方或执行方。  
  - **client agent（A2A client）与 remote agent（A2A server）首现讲解**：  
    - **一句话本质**：client agent 是代表用户发起请求的智能体，remote agent 是接收请求并执行任务的智能体。  
    - **结构化拆解**：  
      - client agent 接收用户目标、向 remote agent 发起任务、在对方要求时补充信息；  
      - remote agent 发布自身描述、处理任务、可请求补充信息、完成后返回消息和生成物；  
      - 在A2A术语中，client agent 也称 A2A client，remote agent 也称 A2A server。  
    - **作用定位**：它们构成A2A交互的请求端与执行端；掌握后能读懂后续三阶段流程。

- **发现阶段**：remote agent 发布 agent card，包含身份、能力、技能、服务端点 URL 和认证要求，供 client agent 发现并判断如何连接。  
  - **agent card 首现讲解**：  
    - **一句话本质**：智能体公开的元数据文档，用于说明自己是谁、能做什么、如何连接和如何认证。  
    - **结构化拆解**：  
      - 内容：身份、能力、技能、服务端点 URL、认证要求；  
      - 形式：机器可读的元数据文档，部署在智能体域名上；  
      - 机制：client agent 读取后获得连接入口和能力判断依据。  
    - **作用定位**：发现阶段的关键入口；掌握它才能理解client如何找到remote并知道认证要求。  
  - **JSON 首现讲解**：  
    - **一句话本质**：一种用键值结构和数组组织数据的文本交换格式。  
    - **结构化拆解**：  
      - 由对象、数组、键值对等结构组成；  
      - 以文本形式表达，机器可读；  
      - 常用于跨系统交换结构化数据。  
    - **作用定位**：agent card 以 JSON 元数据文档形式呈现；理解JSON有助于理解公开描述如何被机器读取。

- **认证授权阶段**：认证通过 agent card 指示的安全方案执行；client agent 认证成功后，remote agent 负责授权并授予访问控制权限。  
  - **认证（authentication）与授权（authorization）首现讲解**：  
    - **一句话本质**：认证确认“你是谁”，授权决定“你能做什么”。  
    - **结构化拆解**：  
      - 认证依据 agent card 中指示的安全方案执行；  
      - 认证成功后，remote agent 负责授权；  
      - 授权结果是访问控制权限。  
    - **作用定位**：建立跨智能体信任；掌握后才能理解为什么发现之后不能直接通信。

- **通信阶段**：client agent 向 remote agent 发送任务；remote agent 处理任务，必要时通知 client 补充信息；完成后向 client 发送消息和生成的 artifact。  
  - **JSON-RPC 2.0 首现讲解**：  
    - **一句话本质**：一种用JSON描述调用请求、响应和错误的消息格式规范。  
    - **结构化拆解**：  
      - 定义调用方法、参数、结果和错误结构；  
      - 使用JSON文本交换数据；  
      - 作为A2A的数据交换格式。  
    - **作用定位**：让不同实现的智能体按统一消息结构通信。  
  - **HTTP/HTTPS 首现讲解**：  
    - **一句话本质**：HTTP是传输超文本和数据的应用层协议，HTTPS是在HTTP基础上增加加密传输的协议。  
    - **结构化拆解**：  
      - HTTP定义请求和响应通信方式；  
      - HTTPS在HTTP通信上增加加密保护；  
      - A2A消息通过HTTPS传输。  
    - **作用定位**：为A2A提供传输通道和传输保护。  
  - **artifact 首现讲解**：  
    - **一句话本质**：智能体在任务中生成的有形输出。  
    - **结构化拆解**：  
      - 形式包括文档、图像、结构化数据；  
      - 随任务完成消息返回给client agent。  
    - **作用定位**：任务结果交付物；理解它才能区分“消息”和“生成物”。

- **长任务与流式更新**：若 agent card 声明 remote agent 支持 streaming，则可用 SSE 推送任务状态更新。  
  - **SSE（Server-Sent Events）首现讲解**：  
    - **一句话本质**：服务器通过一个已打开的HTTP连接持续向客户端推送事件的技术。  
    - **结构化拆解**：  
      - client 建立连接；  
      - remote 通过该连接单向推送状态更新；  
      - 适合需要较长时间完成、涉及人工交互或外部事件的任务。  
    - **作用定位**：让client在长任务中持续获得状态，而不是只等待最终响应。

- **隐私与黑箱协作**：协议将智能体视为 opaque agents，协作时不必暴露内部记忆、专有逻辑或工具实现。  
  - **opaque agents 首现讲解**：  
    - **一句话本质**：协作时只暴露必要接口、不暴露内部实现的智能体处理方式。  
    - **结构化拆解**：  
      - 不公开内部记忆；  
      - 不公开专有逻辑；  
      - 不公开具体工具实现；  
      - 仍可通过标准协议协作。  
    - **作用定位**：保护数据隐私和知识产权，是企业采用A2A的重要收益。

- **标准与阶段**：A2A基于HTTP、JSON-RPC、SSE等既有标准，便于企业采用；但它仍处早期，安全、治理、性能调优仍需改进。  
- **事实与例子**：Google于2025年4月提出A2A；现由Linux Foundation托管开源；旅行规划例子涉及旅行、航班、酒店、游览等多个智能体；artifact可以是文档、图像或结构化数据。
