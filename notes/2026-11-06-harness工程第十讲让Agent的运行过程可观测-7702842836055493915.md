# harness工程第十讲 让Agent的运行过程可观测

# Harness 工程第十讲：让 Agent 的运行过程可观测——学习笔记

## 精华版

本文主线是：Agent 跑完任务后，只看最终汇报无法判断它是否按目标完成；黑盒运行会系统性带来误判、主观评估、盲试重试和会话交接浪费；因此可观测性必须内建为 Harness 的核心架构属性，用运行时信号与过程工件共同解释“系统做了什么”和“为什么这个变更应被接受”，最终让 Agent 基于证据决策，而不是靠猜。

**Agent 快速上手讲解**
1. 一句话本质：Agent 是能接收目标、规划步骤、调用工具或模型并执行多步任务以产出结果的软件实体。
2. 结构化拆解：
   - 组成：目标与上下文、规划决策、工具或模型调用、执行反馈、结果输出。
   - 工作方式：接收任务后拆解步骤，调用可用资源，根据中间反馈迭代，最后输出结果。
   - 关键条件：它需要外部系统提供边界、记录、评估与反馈，否则难以稳定判断自身行为是否正确。
3. 作用定位：本文讨论如何让 Agent 的运行过程被记录、解释和评估，从而提升任务效率与质量。

**Harness 快速上手讲解**
1. 一句话本质：Harness 是包裹 Agent 运行过程的外层工程系统，负责约束、编排、记录、评估与反馈。
2. 结构化拆解：
   - 组成：运行时环境与工具接入、任务编排、信号采集、过程工件管理、评估与重试策略。
   - 工作方式：为 Agent 提供上下文和边界；采集运行行为；保存计划与标准；驱动评估、反馈和迭代。
   - 关键机制：把运行行为与评估信号以可指导下一步决策的形式暴露出来。
3. 作用定位：本文的核心主张是可观测性必须由 Harness 内建，而不是依赖 Agent 自己自觉打日志。

**可观测性快速上手讲解**
1. 一句话本质：可观测性是让系统运行行为与决策意图可被记录、查询、解释并用于下一步决策的能力。
2. 结构化拆解：
   - 运行时层：包含日志、追踪、进程事件、健康检查等信号，回答“系统到底做了什么”。
   - 过程层：包含计划、评分标准、验收条件等过程工件，回答“为什么这个变更应该被接受”。
   - 工作方式：两层一起设计、互相增强；运行时信号解释行为，过程工件解释意图。
   - 本文称为“双层可观测性”：只做好其中一层只能算半成品。
3. 作用定位：它把 Agent 从凭感觉做事转为基于证据做事，直接决定任务效率和质量。

精华版结论：可观测性不是上线后补的日志功能，而是设计阶段就要考虑的 Harness 架构属性；双层可观测性缺一不可；冲刺合同前置对齐目标，评估评分标准保证评估可复现；真实实验显示具体且有证据的反馈能显著降低 Build 成本和时间。

## 整体逻辑链条梳理

1. **问题起点：只看最终汇报无法验证 Agent 是否按目标完成。**  
   成立原因：最终输出不暴露中间状态、执行路径和判断依据，无法判断它是完成了任务，还是绕路、误解或偶然得到结果。衔接：因此需要先看清黑盒运行的代价。

2. **黑盒代价：缺乏可观测性会系统性产生四类问题。**  
   包括难以区分真正正确与看起来正确、评估主观、重试盲猜、会话交接信息断崖。成立原因：没有运行时证据，评估和重试都只能依赖表面结果。衔接：这些代价说明需要把运行行为与决策意图暴露出来。

3. **方向定位：可观测性不是补日志，而是 Harness 的核心架构属性。**  
   可观测性已在精华版讲解，本文采用双层结构：运行时层回答“系统做了什么”，过程层回答“为什么这个变更应被接受”。衔接：下一步需要把抽象能力落成具体构件。

4. **关键构件：任务轨迹、冲刺合同、评估评分标准共同支撑双层可观测性。**  
   **任务轨迹快速上手讲解**
   1. 一句话本质：任务轨迹是一次任务从开始到结束的全程结构化记录。
   2. 结构化拆解：
      - 记录内容：执行动作、使用的上下文、关键状态变化、依据与结果。
      - 工作方式：按时间或步骤串联事件，支持回放，出问题时定位到具体步骤和上下文。
      - 价值条件：记录需结构统一、可查询，并能与评估信号关联。
   3. 作用定位：它是运行时可观测性的核心载体，用于回放 Agent 运行过程、定位失败原因。

   **冲刺合同快速上手讲解**
   1. 一句话本质：冲刺合同是编码开始前生成者与评估者达成的短期任务协议。
   2. 结构化拆解：
      - 组成：任务范围、验收标准、明确不做什么；通常按 Sprint（短迭代周期）推进。
      - 工作方式：开始前对齐目标；完成后生成者先自评，再交给评估者验收。
      - 关键机制：用明确边界防止生成者一开始就跑偏。
   3. 作用定位：它让过程可观察、可验证，是过程可观测性的关键工件。

   **评估评分标准快速上手讲解**
   1. 一句话本质：评估评分标准是把质量判断转成基于证据的分级结构。
   2. 结构化拆解：
      - 组成：评估维度、各维度等级、证据要求、通过条件。
      - 工作方式：把模糊的“好不好”变成可量化等级；不同评估者面对同一输出能给出接近判断。
      - 关键机制：评估反馈必须附带具体证据，而不是只说“不行”。
   3. 作用定位：它保证评估过程可复现，是让 Agent 基于证据修复问题的尺度工具。

   衔接：任务轨迹负责回放，冲刺合同管边界，评分标准管尺度，双层可观测性负责系统层与过程层协同。

5. **为什么不能靠 Agent 自己打日志。**  
   原因有三：Agent 不知道自己不知道什么；日志格式难统一；冲刺合同、评分标准等过程工件需要 Harness 层面支持。衔接：所以可观测性必须由 Harness 内建。

6. **搭建路径：五步把可观测性落到工程里。**  
   采集五类运行时信号、任务前签冲刺合同、建立评估评分标准、用统一追踪链路串联、用规划者/生成者/评估者三角色运行并校准评估者。衔接：方法需要真实实验验证。

7. **实验证据：具体且有证据的反馈能显著降低成本。**  
   真实实验中 Build 成本从约 70 美元降到 36 美元，再降到 5.88 美元；总任务 3 小时 50 分钟、124.7 美元。成立原因：评估反馈足够具体且有证据，模型每轮修复更准，弯路减少。衔接：这说明可观测性带来的是实际效率提升。

8. **收束：可观测性是架构属性，双层缺一不可，前置对齐与评分标准让 Agent 基于证据决策。**  
   练习是审查自身 Harness 差距、为真实任务写冲刺合同、用统一追踪记录完整任务并分析缺失信号。

## 一句话结论

对应链条第 8 环：可观测性必须内建为 Harness 的双层架构属性，用任务轨迹、冲刺合同和评估评分标准把 Agent 的行为与意图变成证据，从而让 Agent 基于证据决策并提升效率与质量。

## 核心要点

对应链条第 1—8 环：

1. 只看最终汇报无法判断 Agent 是否按目标完成，黑盒运行会系统性带来误判、评估主观、盲试重试和会话交接诊断浪费。
2. 可观测性分为运行时层与过程层，分别回答“系统做了什么”和“为什么这个变更应被接受”，两层缺一不可。
3. 任务轨迹、冲刺合同、评估评分标准、双层可观测性是四个关键构件，分别负责回放、边界、尺度和协同。
4. Agent 不会自觉记录所有关键信号，且过程工件需要 Harness 支持，因此可观测性不能外包给 Agent。
5. 搭建路径是采集五类运行时信号、前置冲刺合同、建立分级评分标准、用统一追踪链路串联并复用成熟工具链。
6. 真实实验显示具体且有证据的评估反馈能让 Build 成本从约 70 美元降到 36 美元再降到 5.88 美元，证明可观测性直接节省时间和成本。

## 关键细节

对应链条第 2—7 环。

### 黑盒运行的代价（对应链条第 2 环）

- 难以区分“真的正确”和“看起来正确”：代码审查只能看到代码写了什么，运行时追踪才能说明实际执行了什么；边界条件错误往往只有运行时才暴露。
- 评估容易变悬：没有明确评分标准和验收条件时，不同人对同一输出判断不同，结果也难以复现。
- 重试容易变盲猜：Agent 不知道失败原因，只能在错误方向上反复尝试，浪费 Token 和时间。
- **Token 快速上手讲解**
  1. 一句话本质：Token 是模型处理文本时使用的基本计量单位，不等同于字或词。
  2. 结构化拆解：文本会被切分为 Token；输入和输出都会消耗 Token；上下文长度受 Token 数限制。
  3. 作用定位：本文用它说明盲试重试会直接消耗模型调用成本和时间。
- 会话交接出现信息断崖：进入新会话后系统状态几乎要从零诊断；Anthropic 的观察发现重复诊断可能占整个会话时间的 30% 到 50%。

### 暗色模式效率对比（对应链条第 2—3 环）

- 无可观测性时：计划者描述模糊，生成者凭理解做，评估者只说“感觉不太对”，来回三四轮，45 分钟才勉强做出结果。
- 可观测性完整时：计划者输出清晰冲刺合同，明确改哪些组件、每个组件验证标准、哪些不在范围内；评估者给出带证据意见，例如按钮对比度实测只有 2.1:1，低于无障碍标准要求的 4.5:1。
- **CSS 变量与无障碍对比度标准快速上手讲解**
  1. 一句话本质：CSS 变量是样式表中可复用的自定义属性；无障碍对比度标准规定文本与背景亮度对比的最低比例，常用要求为 4.5:1。
  2. 结构化拆解：CSS 变量集中管理颜色；主题切换通过改变变量值实现；对比度按亮度计算；2.1:1 低于 4.5:1，因此不达标。
  3. 作用定位：它说明“可观测性完整”时评估反馈能具体到可验证证据，而不是主观感觉。
- 结果：15 分钟、一轮迭代得到高质量结果；效率差约三倍，关键区别在可观测性。

### 双层可观测性的具体分工（对应链条第 3 环）

- 运行时可观测性关注系统本身：日志、追踪、进程事件、健康检查等信号，回答“系统到底做了什么”。
- 过程可观测性关注 Harness 决策过程中留下的工件：计划、评分标准、验收条件，回答“为什么这个变更应该被接受”。
- 只有日志时，只能知道系统出错；有合同、评分标准和验收条件后，才能判断为什么这么改、改动该不该被接受。

### 四个关键概念的职责（对应链条第 4 环）

- 任务轨迹：任务从开始到结束的全程记录，包含做了什么、依据什么上下文、在哪一步发生变化；出问题可回放定位。
- 冲刺合同：编码前先达成的短期协议，写清任务范围、验收标准、明确不做什么；后续工作才有边界。
- 评估评分标准：把质量评估从主观感觉变成基于证据的结构判断，让不同人看同一输出能得出相近结论。
- 双层可观测性：系统层和过程层一起设计、互相增强，既看系统跑得稳不稳，也看任务推进得对不对。

### 为什么 Agent 不能自己打日志（对应链条第 5 环）

- Agent 不知道它不知道什么：不会主动记录自己尚未意识到重要的信号；没有外部约束时只记自己觉得重要的内容，但往往不够。
- 日志格式难统一：不同会话各写各的，今天这样记、明天那样记，难以系统化分析。
- 过程可观测性不是简单打日志：冲刺合同、评分标准是结构化工件，需要 Harness 层面支持。
- 结论：可观测性必须由 Harness 内建，不能指望 Agent 自觉完成。

### 五步搭建方法（对应链条第 6 环）

1. 把运行时信号采集内置到 Harness，重点采集五类信号：
   - 应用生命周期：启动、持续运行、关闭等关键阶段状态。
   - 功能路径执行：关键路径的入口、检查点、出口。
   - 数据流：数据在组件之间如何流转。
   - 资源利用：尤其内存持续增长等异常模式。
   - 错误和异常：必须带完整上下文，不能只有简单错误消息。
2. 任务开始前先签冲刺合同：生成者和评估者先对齐目标，写清做什么、做到什么程度通过、哪些不做。
3. 建立评估评分标准：把模糊的“好不好”变成可量化等级，例如代码正确性从所有测试通过到编译失败分成 A 到 D 层级。
4. 用 OpenTelemetry 统一信号与追踪链路。
   **OpenTelemetry 与追踪链路快速上手讲解**
   1. 一句话本质：OpenTelemetry 是一套跨语言、跨平台的遥测数据标准与工具集，用于统一生成、采集、传输追踪等信号。
   2. 结构化拆解：
      - 数据模型：Trace 表示一次执行链路，Span 表示链路中的一段操作，属性用于标注关键信息。
      - 采集方式：通过 API/SDK 生成数据，按标准协议导出。
      - 分析方式：数据可接入 Jaeger、Zipkin 等追踪存储与可视化工具，复用成熟分析能力。
   3. 作用定位：本文用它把 Harness 会话、任务、验证步骤串成清晰链路，避免自造存储、分析和可视化系统。
   - 组织方式：每个 Harness 会话对应一个 Trace，每个任务对应一个 Span，每个验证步骤再拆成 Span；哪一步出问题就沿 Trace 查上下文。
5. 用三个各司其职的 Agent 运行并校准：
   - 规划者：接收一到四句话的简短需求，扩展成完整产品规格；原则是大胆设定范围、专注高层设计，避免过早陷入细节导致错误传导下游。
   - 生成者：按 Sprint 一个功能一个功能推进；每个 Sprint 前先与评估者协商合同，明确完成标准；完成一轮自评后交给评估者验收。
   - 评估者：用 Playwright 以真实用户操作方式点击运行中的应用，检查实际效果。
   **Playwright 与浏览器自动化验证快速上手讲解**
   1. 一句话本质：Playwright 是浏览器自动化测试工具，用代码驱动浏览器执行点击、输入和断言。
   2. 结构化拆解：启动浏览器；执行用户操作；检查页面状态；生成测试结果和证据。视觉回归是对比页面截图差异；端到端测试是从用户入口到结果的完整流程测试。
   3. 作用定位：评估者用它验证运行中应用的实际效果，并提供具体证据，而不是只说“不行”。
   - 评估维度：产品深度、功能性、视觉设计、代码质量；任一维度不达标，该 Sprint 判失败，反馈附具体证据。
   - 评估者校准：早期评估者会发现问题后又说服自己问题不严重；团队通过读日志找到其判断与人类判断的偏差，有针对性地更新 Prompt。
   **Prompt 快速上手讲解**
   1. 一句话本质：Prompt 是提供给模型的指令与上下文文本，用于约束和引导模型输出。
   2. 结构化拆解：包含角色与任务说明、约束与格式要求、示例与上下文；更新 Prompt 可改变模型判断倾向。
   3. 作用定位：本文中团队通过更新 Prompt 校准评估者，使其评分更合理。

### Anthropic 实验数据（对应链条第 7 环）

- Anthropic（AI 研究机构）在 2026 年 3 月做了系统性 Harness 实验，用三种不同架构完成同一任务：用 WebAudio API 做浏览器端应用。
- **WebAudio API 快速上手讲解**
  1. 一句话本质：WebAudio API 是浏览器提供的音频处理接口，用于在网页中生成、处理、分析音频。
  2. 结构化拆解：创建音频上下文；用节点图组织音频处理；控制参数；进行实时处理。
  3. 作用定位：本文实验用它作为浏览器端应用任务，验证不同 Harness 架构的效果。
- 阶段数据：
  - 规划阶段：4.7 分钟，成本 4 毛 6 美元（原文），非常轻。
  - 第一轮 Build：2 小时 7 分钟，成本 71 美元。
  - 第二轮 Build：成本 36 美元。
  - 第三轮 Build：10 分钟，成本 5 块 8 毛 8 美元。
  - 总任务：3 小时 50 分钟，总成本 124 美元 7 毛。
- Build 轮次成本曲线从约 70 美元降到 36 美元，再降到 5.88 美元，接近断崖式下降。
- 原因：评估者反馈足够具体且有证据支撑，模型每轮修复更准，弯路越来越少。

## 原文文案

大家好，欢迎来到第十讲。今天我们要聊一个特别关键的话题，就是怎么让 Agent 的运行过程变得可观测。在正式开始之前，我想先请大家想一个问题。你的 Agent 跑完一个任务之后，你到底是怎么知道它做得对不对的。它是真的按你的要求完成了，还是中间偷偷绕了路，甚至干脆理解错了你的意思。如果你现在的答案是，我只能靠它最后给我一句汇报。那今天这讲的内容，你可一定要认真听。因为这一讲，我们要打破一个常见的误区，很多人觉得可观测性就是多打点日志，方便出问题了去查一查。但今天我要告诉你的是，可观测性绝对不是锦上添花的日志，它是 Harness 的一个核心架构属性，它直接决定了你的 Agent 工作起来的效率和质量。那接下来，我们会分两步走。第一步，我们先来看看，如果 Agent 是一个黑盒，你到底要付出多大的代价。第二步，我们再一起看看，怎么系统地、一步步地把可观测性给搭建起来。好，我们开始。

我们先来看一个很常见的真实场景。一个 Agent 跑了 20 分钟，改了一大堆文件，最后很自信地告诉你，做完了，但有两个测试失败。你再问它，为什么会失败？它说不确定，可能是时序问题。你又问它，到底改了哪些关键路径？它又说，让我再看看代码。这其实不是 Agent 笨，而是它自己也不清楚，运行时到底发生了什么？问题根源在于，Harness 缺乏可观测性。Agent 看不到运行过程中的真实状态，拿不到足够的证据，就只能靠猜来做判断。一旦没有可观测性，评估就会变成主观感觉，重试也会变成盲目摸索。所以，OpenAI 和 Anthropic 都把可靠性看成一个证据问题。Harness 必须把运行时行为和评估信号清楚地暴露出来，而且要能以指导下一步决策的形式呈现。这样，Agent 才能从凭感觉做事，变成基于证据做事。

当 Harness 缺乏可观测性时，问题往往不是偶然出现，而是会系统性地冒出来。首先，我们很难区分真的正确和看起来正确。代码审查，只能看到代码写了什么。但运行时追踪才能告诉我们它实际执行了什么。很多边界条件上的错误，只有在真正运行的时候才会暴露出来。其次，评估会变成一件很悬的事情。如果没有明确的评分标准和验收条件，不同人对同一个输出可能会有完全不同的判断，结果也很难复现。第三，重试会变成盲猜。Agent 并不知道到底为什么失败，于是只能在错误的方向上反复尝试，白白消耗 Token，也浪费时间。最后，会话交接时会出现信息断崖。一旦进入新的会话，系统状态几乎要从零开始诊断。Anthropic 的观察发现，这种重复诊断可能占到整个会话时间的 30% 到 50%，也就是说真正的浪费，往往不是发生在你看得见的地方，而是发生在你看不见的地方。

我们来看一个特别直观的效率对比，同样是给应用添加暗色模式，如果没有可观测性，计划者只能给出很模糊的描述，生成者凭自己的理解去做，评估者看完也只有一句，感觉不太对。到底哪里不对，说不清楚。于是，生成者只能反复试，来回三四轮，四十五分钟才勉强做出一个结果。但如果可观测性足够完整，情况就完全不同。计划者会输出一份清晰的冲刺合同，明确要改哪些组件，每个组件的验证标准是什么，哪些内容不在本次范围内。生成者按合同实现，评估者也能给出带证据的具体意见。比如，按钮对比度实测只有 2.1 比 1，低于无障碍标准要求的 4.5 比 1。这样一来，15 分钟，一轮迭代就能得到高质量结果。同样是做暗色模式，效率差了三倍，关键区别就在可观测性。

可观测性可不是简单的多打几条日志。它其实要分成两层，而且缺一不可。第一层是运行时可观测性。它关注的是系统本身，比如日志、追踪、进程事件、健康检查这些信号。它回答的问题是，系统到底做了什么？第二层是过程可观测性。它关注的是 Harness 在决策过程中留下的工件，比如计划、评分标准、验收条件。它回答的问题是，为什么这个变更应该被接受？换句话说，运行时信号解释的是行为，过程工件解释的是意图。如果只有日志，你只知道系统出错了，但有了合同、评分标准和验收条件，你才能判断它为什么这么改？以及这个改动，到底该不该被接受？所以，这两层必须一起设计，互相增强，只做好其中任何一层都只能算半成品。

我们来把这一讲最关键的四个概念串起来，首先是任务轨迹。它就像一个任务从开始到结束的全程记录，具体做了什么，依据什么上下文，在哪一步发生了变化，都会被完整留下来。一旦出了问题，我们可以把整个过程回放出来，快速定位原因。其次是冲刺合同。它是在编码开始之前先达成一个短期协议，把任务范围、验收标准，以及明确不做什么，先说清楚。这样后续工作才有边界，过程也才真正可观察、可验证。第三是评估评分标准。它的作用是把质量评估从主观感觉变成基于证据的结构判断，让不同的人看同一个输出，也能得出相近的结论。最后是双层可观测性，也就是说，系统层和过程层要一起设计，互相增强，既看系统跑得稳不稳，也看任务推进得对不对。记住这四个关键词，任务轨迹、冲刺合同、评估评分标准、双层可观测性。后面的搭建方法，都会围绕它们展开。

你可能想问，Agent 不能自己打日志吗？答案其实是，基本不能。第一个原因是，Agent 不知道它不知道什么。它不会主动记录那些自己还没意识到重要的信号。没有外部约束的话，它只会记自己觉得重要的内容，但它觉得重要的，往往并不够。第二个原因是，日志格式很难统一。不同会话各写各的，今天这样记，明天那样记，最后很难做系统化分析。第三个原因更关键，过程可观测性不是简单打日志就能解决的。像冲刺合同、评分标准这些内容都是结构化的工件，需要 Harness 层面提供支持，不是多打印几行日志就能搞定的。所以结论很明确，可观测性必须由 Harness 内建，而不是指望 Agent 自己自觉完成。

第一步，我们要把运行时信号采集，直接内置到 Harness 里，而不是依赖 Agent 自己打日志。重点采集五类信号，第一，应用生命周期，包括启动、持续运行和关闭这些关键阶段的状态。第二，功能路径执行，关键路径的入口、检查点和出口都要留下记录。第三，数据流，数据在组件之间怎么流转，要看得清楚。第四，资源利用。尤其是内存持续增长，这类异常模式。第五，错误和异常。而且必须带上完整上下文，不能只有一条简单的错误消息。这样采集之后，运行时出现任何异常，我们都能在信号里找到对应证据，定位问题就不再靠猜，而是靠查。

接下来，我们要在任务真正开始前，先签一份冲刺合同。也就是说，生成者和评估者要先对齐目标，把话说清楚。这次到底做什么，做到什么程度才能通过。拿暗色模式举例，合同里会写明，范围包括修改主题切换组件、更新全局 CSS 变量、补充暗色模式测试。验证标准也很明确，就是视觉回归要通过，端到端测试要通过，而且不能出现样式闪烁。同时，还要提前说清楚哪些不做，比如打印样式和第三方组件，这次先不处理。这样做的好处是避免生成者一开始就跑偏，做出评估者一眼就会否掉的结果。

再往后，是第三步建立评估评分标准。我们要把模糊的好不好，变成可以量化的等级。比如代码正确性，可以从所有测试通过，到编译失败，分成 A 到 D 几个层级。这样一来，不同评估者面对同一个输出，也能给出接近的判断。所以，这两件是一个管边界，一个管尺度。冲刺合同防止方向跑偏，评分标准保证评价一致。

第四步，我们用 OpenTelemetry 把这些信号统一起来。简单来说，就是给每一次执行过程建立一条清晰的追踪链路。每个 Harness 会话对应一个 Trace，每个任务对应一个 Span，每个验证步骤再往下拆成 Span。同时，我们用标准属性把关键信息标注出来。这样一来，整个结构就变得非常清楚，一个会话里面包含多个任务，一个任务里面又包含多个验证步骤。哪一步出了问题，都可以顺着这条 Trace 一路查下去，快速定位到当时的上下文。这么做最大的好处是，我们不需要自己重新造一套可视化、存储和分析系统。因为这些可观测性数据本身就是标准格式，可以直接接入 Jaeger、Zipkin 这些成熟工具链，生态里已有的分析能力也都能直接复用。

那这套方法，到底有没有效呢？我们来看一个真实实验，Anthropic 在 2026 年 3 月做了一次系统性的 Harness 实验，他们用三种不同的架构去完成同一个任务，也就是用 WebAudio API 做一个浏览器端的应用。从阶段数据来看，规划阶段只花了 4.7 分钟，成本是 4 毛 6 美元，非常轻。真正的大头在第一轮 Build 花了两个小时 7 分钟，成本达到 71 美元。但有意思的是，后面的成本没有一直高下去，而是快速下降。第二轮 Build 降到了 36 美元，到第三轮 Build，只用了 10 分钟，成本也降到 5 块 8 毛 8。最后整个任务总共花了 3 个小时 50 分钟，总成本是 124 美元 7 毛。如果我们单独看 Build 轮次的成本曲线，会发现它几乎是断崖式下降，从 70 到 36 再到 5 块 9。为什么会这样？关键就在于评估者给出的反馈足够具体，而且有证据支撑，所以模型每一轮修复都更准，弯路越来越少。所以，这里看到的不是抽象的方法论，而是非常直接的效率提升，可观测性带来的不只是更清楚的过程，而是真金白银的时间和成本节省。

接下来，这套系统的关键是三个各司其职的 Agent。第一个是规划者，它接收到的需求通常很短，可能只有一到四句话，它要做的是把这些简短想法扩展成一份完整的产品规格。这里有一个很重要的原则，规划者要大胆设定范围，专注高层设计，而不是一开始就陷入细节。因为，如果它太早把细节定死，一旦某个地方判断错了，这个错误就会一路传导到下游，后面越做越偏。第二个是生成者，它会按照 Sprint 一个功能一个功能地推进，每开始一个新的 Sprint 之前，它都会先和评估者协商一份合同，明确做到什么程度才算完成。等生成者自己完成一轮自评之后，再交给评估者验收，这样每个阶段都有清晰标准，而不是凭感觉交付。第三个是评估者，它会用 Playwright 像真实用户一样，去点击正在运行的应用，检查实际效果。评估维度也很明确，包括产品深度、功能性、视觉设计和代码质量。只要任何一个维度不达标，这个 Sprint 就会被判失败，而且反馈里还会附上具体证据，不是简单说一句不行。不过，评估者也不是一开始就这么可靠，早期它也会发现问题，但又会说服自己，觉得问题不严重。后来团队通过读日志，找到它的判断和人类判断出现偏差的地方，再有针对性地更新 Prompt，经过几轮调整，它的评分才真正变得合理。

最后，我们用三句话来收束今天的内容。第一，可观测性不是系统上线后才补上的功能，而是 Harness 的架构属性。它必须在设计阶段就被认真考虑，成为核心能力的一部分，而不是事后打补丁。第二，双层可观测性缺一不可。运行时信号告诉我们系统正在发生什么，过程工件则解释系统为什么这样做。只有把两者结合起来，我们才能真正理解 Agent 的行为，而不是只看到表面结果。第三，冲刺合同同样前置对齐工作目标，评分标准要让评估过程可复现。这样做的目的是让 Agent 基于证据做决策，而不是在猜测中摸索前进。课后也给大家留了三个练习。第一，审查你自己的 Harness，找出可观测性上的差距。第二，为一个真实任务写一份冲刺合同，并对比它带来的效果变化。第三，用 OpenTelemetry 记录一次完整任务的执行轨迹，分析哪里还缺少信号支持。谢谢大家。
