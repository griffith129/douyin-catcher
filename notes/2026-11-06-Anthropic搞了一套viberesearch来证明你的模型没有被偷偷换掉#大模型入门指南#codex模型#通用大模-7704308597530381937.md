# 视频笔记：FlashProof 与可验证模型权重

## 精华版

视频介绍一套开源验证系统 FlashProof：服务商公开绑定模型权重的指纹，并为每次回答附上证明；用户用问题、回答、指纹和证明在普通 CPU 上约 20 秒验证。它针对 API 权重保密、服务商可能悄悄换成更便宜或更小模型的问题，把“相信服务商”变成“检查证明”。机制上把权重编码为混入随机数的大表并用哈希锁定，将计算化简为数学条件，验证时随机抽查少数列，安全性在 Lean 中做过机器检查。因浮点计算无法逐位核对，系统证明的是整数版本；严格标准在真实浮点服务中不实用，测试两个推理引擎各 96 条正常回答无一通过，故采用宽松标准，通过只说明回答与模型“差得不多”。证明生成很慢很贵：H100 每秒约 110 个 token，比 vLLM 慢 90 多倍，需约 90 多张卡。且证明只绑定 Commitment ID 对应的权重，不证明模型身份，ID 需来自可信第三方。论文代码与 Lean 证明几乎全由 AI 在人的指导下完成，测试审阅也由 AI 做，尚无独立复核。结论：它已在 4000 亿参数 Llama 4 Maverick 上跑通，但仍是慢、贵、采用宽松标准的研究原型。

## 整体逻辑链条梳理

1. **问题成立**：API 场景中权重保密，用户看不到服务商实际跑什么，已有研究审计 API 背后可能被换成更便宜、更小或压缩过的模型；因此“只能相信服务商”是真实痛点。
2. **目标设定**：需要一种不泄露权重、又能让用户检查回答是否来自某套权重的方法；FlashProof 把“相信”变成“检查”。
3. **流程闭环**：Commit 公开绑定权重的 64 位 Commitment ID；每次回答由 GPU 生成证明；用户用 ID、证明、问题、回答在 CPU 上验证，约 20 秒得到通过或拒绝。
4. **机制支撑**：权重被编码成混入随机数的大表并用哈希锁住；计算化简为关于表的数学条件；验证时随机抽查少数列，抽出的列混有随机数，单看与原始权重无关；安全性在 Lean 中做过机器检查的数学证明。
5. **工程适配**：浮点数在不同机器上算结果有细微差别，无法逐位核对，所以证明整数版本；严格标准要求每个词都是整数版本第一选择，但真实浮点服务约 7% 位置第一名不同，测试的 192 条正常回答无一通过，因此实际采用宽松标准。
6. **代价与边界**：宽松标准只要求每个词分数离第一名不远，通过只说明回答和模型差得不多，不能证明就是它给的；整套方法按 temperature 0 对比，随机采样难分辨；证明事后另算且很慢，H100 每秒约 110 token，比 vLLM 慢 90 多倍，约需 90 多张卡；证明只说明来自 Commitment ID 对应权重，不说明是哪家哪个模型，ID 必须来自可信第三方。
7. **现状与结论**：论文代码和 Lean 证明几乎全由 AI 在人的指导下写，测试审阅也由 AI 做，目前无人独立复核；仓库首页有提示词可交给 Coding Agent 编写验证程序。FlashProof 已在 4000 亿参数 Llama 4 Maverick 上跑通，但仍是慢、贵、研究原型；若服务商采用且 ID 可信，用户买 API 时就能检查模型是否被偷偷替换。

## 术语首现讲解

- **FlashProof**  
  - 一句话本质：一套让服务商在不泄露模型权重的情况下，为回答附带可验证证明的开源系统。  
  - 结构化拆解：由 Commit 公开指纹、回答时生成证明、用户端 CPU 验证三部分组成；关键机制是权重编码成大表、哈希锁定、随机抽查数学条件；作用是把对服务商的信任转成可执行检查。  
  - 作用定位：本文档的核心对象；理解它后可知道“可验证模型权重”在 API 场景中解决什么问题、代价和边界在哪里。

- **模型权重**  
  - 一句话本质：模型训练后得到的大量参数数值，决定模型输出。  
  - 结构化拆解：由大量数值组成；服务商通常保密；FlashProof 用 Commitment ID 绑定一套权重但不公开权重本身；证明只说明回答来自该 ID 对应权重。  
  - 作用定位：它是被验证的对象；理解它才能明白为什么“看不到权重也能检查”需要密码学与抽查机制。

- **API**  
  - 一句话本质：一方调用另一方模型服务的接口。  
  - 结构化拆解：用户发送问题，服务商返回回答；页面可标注所用模型；但权重保密，用户无法直接确认实际模型；FlashProof 试图让每次回答附带可验证证明。  
  - 作用定位：本文的问题场景；掌握它后可理解模型替换风险和验证需求的实际来源。

- **Commitment ID**  
  - 一句话本质：一串 64 位标识，用来绑定一套模型权重。  
  - 结构化拆解：服务商公开该 ID；权重仍保密；证明与 ID 对应；用户验证时需同时使用 ID、证明、问题和回答；ID 必须来自可信第三方，不能从被检查服务器获取。  
  - 作用定位：它是验证链条的锚点；理解它才能明白“证明只绑定权重，不证明模型身份”这一边界。

- **哈希**  
  - 一句话本质：把数据映射为固定长度摘要的方法。  
  - 结构化拆解：FlashProof 用哈希把混入随机数的大表锁住；验证时检查与表相关的数学条件；抽查少数列即可确信条件成立。  
  - 作用定位：它支撑“不泄露权重也能检查”的机制；理解它有助于明白证明为何不暴露原始权重。

- **Lean**  
  - 一句话本质：一种可机器检查数学证明的工具。  
  - 结构化拆解：FlashProof 的安全性在 Lean 中做过机器检查的数学证明；论文称几乎全部代码和 Lean 证明由 AI 在人的指导下写；测试和审阅也由 AI 做，目前无人独立复核。  
  - 作用定位：它提供形式化安全论证；理解它可知道该系统安全性论证的来源与“未经独立复核”的风险。

- **浮点数 / 整数版本**  
  - 一句话本质：浮点数是带小数近似的计算格式，整数版本是只用整数计算的模型版本。  
  - 结构化拆解：同一模型用浮点数在不同机器上算结果有细微差别，无法逐位核对；FlashProof 证明整数版本，因整数计算在哪台机器上都完全一样；但真实服务用浮点数，与整数版本约 7% 位置第一名不同。  
  - 作用定位：它解释严格标准为何不实用、为何要采用宽松标准；理解它可明白验证精度与实用性的取舍。

- **推理引擎 / temperature 0 / vLLM / H100 / token**  
  - 一句话本质：这些是模型生成回答与性能测量相关的工程名词。  
  - 结构化拆解：推理引擎负责生成回答；temperature 0 表示按确定性方式对比；vLLM 是同一张卡上处理 token 的推理系统；H100 是 GPU；token 是文本处理单位。视频称一张 H100 每秒只能给约 110 个 token 出证明，比 vLLM 处理这些 token 慢 90 多倍，要给一张卡上全部请求出证明约需 90 多张卡。  
  - 作用定位：它们说明 FlashProof 的证明生成代价；理解它们可判断该方法当前为何只是研究原型。

- **Coding Agent**  
  - 一句话本质：可执行编程任务的 AI 代理。  
  - 结构化拆解：仓库首页给了一段提示词，可交给自己的 Coding Agent 去编写验证程序、检查形式证明；论文称代码、Lean 证明、测试和审阅大量由 AI 完成。  
  - 作用定位：它体现该项目开发与审阅方式的特殊性；理解它可关注“AI 生成证明与代码是否需要独立复核”的问题。

## 一句话结论

FlashProof 通过“Commit 权重指纹—生成回答证明—CPU 抽查验证”的流程，让用户在不看权重的情况下检查 API 回答是否来自承诺的模型权重，把对服务商的信任变成可验证检查；但它仍慢、贵、采用宽松标准，只绑定权重 ID 不证明模型身份，且未经独立复核，目前只是跑通 4000 亿参数规模的研究原型。
