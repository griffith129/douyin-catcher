# 不要乱给上下文增加工具! #Agent #AI #面经 #程序员 #校招

# 学习笔记：不要乱给上下文增加工具

## 精华版

视频反对为了降低表面 Token 占用，在对话中途随意增加外部工具信息。工具信息默认处在上下文开头，中途新增会改动开头段落，使已有计算结果缓存失效；失效后的重复计费可能远高于省下的 Token。更稳妥的做法是使用接口提供的按位置插入工具和延迟加载工具定义能力，以保留已有缓存前缀。视频还指出，工具字段独立且不可改是早期模型能力限制留下的历史设计。

## 整体逻辑链条梳理

1. 常规会话信息按顺序进入模型，新增对话内容通常追加在末尾；因此直觉上新增工具也应加在末尾。
2. 但工具定义由模型接口以独立字段传入，默认位于上下文开头，开发者只能选择传哪些工具，不能直接决定工具定义的位置。
3. 中途新增工具会更新开头的工具定义段落，使整个上下文的缓存前缀改变，导致已有缓存失效并重新计费。
4. “会话开始清空工具、需要时再加回”看似减少 Token 占用，实则每次加工具都可能丢弃缓存；在缓存命中与未命中价格比为 50:1 时，上下文超过临界点就会亏损。
5. 新机制用按位置插入工具和延迟加载工具定义解决：前者让工具从插入位置生效并保留前文，后者让工具定义先不进入上下文，需要时再加载。
6. 工具字段独立不可改源于早期模型只在特定上下文位置学会使用工具，后续虽模型变强，该设计仍被保留。

## 一句话结论

不要为了省表面 Token 在会话中途随意增加工具定义；这会破坏已有缓存并可能增加总成本，应使用按位置插入和延迟加载等机制。

## 核心要点

- 工具定义（本质：告诉模型可调用哪些外部能力的声明；拆解：包含工具名称、用途说明、参数结构，由 LLM API 作为独立字段接收，模型据此判断何时调用与如何填参数；作用定位：决定模型当前可用工具集，其内容和位置变化会影响上下文缓存与计费）默认位于上下文开头，且开发者不能直接修改其位置。
- 中途新增工具会更新开头工具段落，使 KV Cache（本质：模型对已处理上下文的中间计算结果缓存；拆解：按上下文前缀保存键值状态，前缀不变可复用，修改开头会使后续缓存失效；作用定位：减少重复计算与重复计费，是长对话成本的关键）失效并重新计费。
- “会话开始清空工具、按需加回”看似省 Token，实则可能因每次加工具都丢缓存而亏损。
- 在缓存命中与未命中价格比为 50:1 时，若当前会话有 N 条消息、工具长度为 T，则上下文长度超过 H=T/49 时，费用上会出现亏损。
- OpenAI Responses API（本质：OpenAI 的模型响应接口；拆解：通过 input 按顺序传递消息和插入项，并返回模型输出；作用定位：承载本视频的按位置插入工具方案）中的 additional_tools（本质：允许在 input 中插入工具定义的抽象；拆解：插入 role 为 developer 的 additional_tools 后，工具从插入位置开始可用，前文按原顺序保留；作用定位：避免改动开头工具列表，维持缓存前缀）可在对话中途插入工具。
- defer_loading（本质：延迟加载工具定义的开关；拆解：工具定义正常传给 API 但设 defer_loading=true，模型初始不加载完整定义，需要时先搜索工具再加载并调用；作用定位：减少初始工具定义占用的 Token，并保留已有提示词缓存）可减少工具很多时的初始上下文占用。

## 关键细节

- 标准 LLM API 消息构成包括系统提示词、用户消息、工具返回结果等；外部信息通过 Messages 传递，唯有工具定义以单独字段传给 API。
- 默认情况下，新增工具会导致上下文最开始部分的工具定义段落更新，并导致整个上下文被重新载入缓存。
- 视频批评的“野鸡项目”做法：会话一开始将工具全部清空，再通过关键词检测或其他意图识别机制，在需要时把工具定义加回上下文；表面看几十个工具的上下文占用被清理，但每次额外加入工具都会丢弃原本的 KV Cache。
- 成本计算例子：缓存命中价格与未命中价格比为 50:1；当前会话有 N 条消息且工具长度为 T；若当前上下文长度超过临界点 H=T/49，则在 Token 费用上出现亏损。
- OpenAI Responses API 示例：对话先提出讨论订单问题；随后在 input 中插入 role 为 developer 的 additional_tools，用于定义查询客户的 GetCustomer 工具；最后才提出查询客户 42；这样工具从插入位置开始供模型使用，前面的对话内容仍按原顺序保留，长对话中按原位置保留插入项有助于维持此前的缓存前缀。
- defer_loading 示例：仍正常将 Tools 定义传递给 LLM API，但设置 defer_loading=true；API 收到工具定义，模型一开始却不加载进上下文；用户问北京天气时，Claude 先通过工具搜索找到 GetWeather，再加载完整定义并调用；工具很多时，这能减少初始进入上下文的工具定义所造成的 Token，也有助于保留已有提示词缓存。
- 历史遗留原因：LLM API 的工具字段一直是独立、不可改字段；早期 LLM API 即使经过后训练，也只能学会特定上下文位置的工具使用，工具定义放到其他位置可能完全不会用；后续模型变强，但该设计仍被保留。

## 原文没有讲清的问题

- H=T/49 的推导细节未展开：N 条消息、T 工具长度、缓存粒度、50:1 价格比分别如何影响实际盈亏，工程中如何估算。
- additional_tools 与 defer_loading 的适用模型、API 范围、兼容性和跨厂商支持情况未说明。
- 按位置插入工具后，缓存前缀保留的具体机制与限制未展开；插入项在长对话中如何管理、删除或迁移也未说明。
- 关键词检测或意图识别误判导致工具未加、加错或延迟加载失败时，成本与可靠性影响未讨论。
- 工具定义位置对当前模型工具调用能力的影响是否仍存在，视频只提到历史原因，未给出当前模型的表现差异。
- 视频结尾提到“模型网关”但未展开；它如何统一处理工具定义、缓存与多模型路由，仍是开放问题。
- 逻辑链回收：第 1—2 环解释工具位置为何特殊，第 3 环解释缓存为何失效，第 4 环解释亏损条件，第 5 环给出解决机制，第 6 环解释历史成因；尚未闭环的是 H 推导细节、跨厂商兼容性、插入项生命周期与模型网关方案。

## 原文文案

绝大部分 AI 教学视频，通常会这么介绍大模型的上下文构成：系统提示词在最开头，紧接着是工具定义，最后是用户的对话消息。之后，对话增加了一些内容都以 Append 的形式放在上下文的最末尾，又因为上下文通常有 Token 的长度限制。Agent 项目都会主动进行上下文压缩，为了实现上下文压缩，程序员们不约而同地盯上了那些长的工具定义。小学二年级的同学都知道，大模型会将会话上下文加入 KV Cache 做缓存，如果修改过去已经完成的上下文，会导致 KV Cache 缓存失效，从而增加 Token 成本。实际上说，增加工具信息怎么说也应该是默认增加在上下文的最末端，按说不会出差子，但实际上几乎所有的 LLM API 增加外部工具时，新的工具定义都会被加到模型开始处，而不是结尾。这里展示给大家的是一个标准的 LLM API 消息构成，如图系统提示词、用户消息、工具返回结果。外部信息插入，全部都是在 Messages 这里被传递给 LLM API 服务器的，唯有工具定义是以单独的字段被传递给 LLM API 使用者，没有权限修改 LLM 上下文的构成模式，他们只能选择将哪些工具传递给 API，而无法主动选择工具定义被放在上下文的哪个位置。而默认情况下，新增的工具会导致上下文最开始部分的工具定义段落发生更新，并导致整个上下文被重新载入缓存。在一些半吊子的野鸡项目中，开发者为了降低明面上的 Token 消耗量，会在会话的一开始将工具全部清空。随后通过关键词检测，或者其他意图识别机制在需要的时候把工具定义加回上下文，他们肯定觉得自己这样很聪明，明面上说，几十个工具的上下文占用全被清理干净了。会话开始时的上下文数量会显著降低，但后果是每当一个额外的工具在后续对话中被加入上下文，原本的 KV Cache 都将被迫被丢弃。如图额外的 Token 损耗，可以被很容易地计算出来，若模型 API 的缓存命中价格与缓存未命中价格比为 50 比 1。假设当前会话有 N 条消息且工具长度为 T。若当前上下文长度超过临界点，H 等于 T 除以 49，则在 Token 费用上出现亏损。今年，OpenAI 在 Responses API 中提供了 additional_tools 这种抽象，在这段代码中对话先提出讨论订单问题。随后在 input 中，插入一个 role 为 developer 的 additional_tools，用于定义查询客户的 GetCustomer 工具，最后才提出查询客户 42，这样工具会从插入的位置开始供模型使用，前面的对话内容仍按原顺序保留，对于长对话按原位置保留这个插入项，也有助于维持此前的缓存前缀，避免因为改动开头的工具列表而影响缓存命中。另外一项与此相关的扩展能力是 defer_loading。图中我们仍然正常将 Tools 定义传递给 LLM API，但给它设置的 defer_loading 等于 true，这意味着 API 收到的工具定义，模型一开始却不会把它加载进上下文。当用户问北京天气如何时，Claude 可以先通过工具搜索，找到 GetWeather，再加载它的完整定义并调用。工具很多时，这能减少一开始进入上下文的工具定义所造成的 Token，也有助于保留已有的提示词缓存。出于一些历史遗留问题，LLM API 的工具字段一直是一个独立的、不可改字段。早期 LLM API 十分愚蠢，即使通过后训练也只能学会特定上下文位置的工具使用，如果工具定义被放在其他位置，它可能就完全不会用了。虽然在接下来几年大模型一天比一天强，但是这个设计还是被保留了下来，本期介绍到此结束，相信视频大概会介绍模型网关。喜欢的话，可以关注一波，谢谢大家。
