## 精华版

视频反对让多个自动写码与审查系统只根据代码文本互相挑错；这种做法容易产生大量误报，却漏掉真实运行才暴露的问题，还会把少量改动膨胀成大量补丁。作者主张两条路：具体功能先写测试、再实现，并把程序真实跑起来验证；复杂架构用可穷举所有执行步序的数学方法验证。质量机制应看两个指标：真实线上故障能否被全部拦住，以及每拦住一个真问题要处理多少误报。省下互审消耗，回到这两条路。

## 整体逻辑链条梳理

1. 作者先否定“让多个模型只读代码互审”的路线，因为其脱离运行环境。  
2. Laurent 在 Pistachio 中砍掉对抗性代码审查，作为现实案例支撑第 1 环。  
3. 对抗性审查失灵的机制是：模型算不清全局条件、不运行程序，只能按字面猜。  
4. 为交差而报风险，导致假警报；写码模型为过关加入冗余逻辑，导致补丁膨胀，同时漏掉真实运行问题。  
5. 正路一：具体功能用先写测试、再实现、真实运行验证。  
6. 正路二：复杂架构用大模型辅助形式化验证，穷举执行步序。  
7. 质量机制要用真实故障拦截率和假警报/真问题比来衡量。  
8. 结论：省下互审消耗，回到 TDD 与形式化验证两条正路。  

## 一句话结论

对应链条第 8 环：视频主张放弃让大模型做脱离运行环境的对抗性代码审查，具体功能走 TDD 与真实运行验证，复杂架构走形式化验证（TLA+ / Kani）。

### 首现讲解：大模型

1. **一句话本质**：大模型是用大量文本训练、能根据输入生成文本输出的模型。
2. **结构化拆解**：
   - 由大量文本训练形成；
   - 接收输入文字并逐段生成输出；
   - 本身不执行代码，也不天然读取运行环境。
3. **作用定位**：本文中它是写代码、审查代码、辅助形式化验证的主体；理解其“会生成、但不自动运行”的边界，才能判断哪些任务适合它。

### 首现讲解：对抗性代码审查

1. **一句话本质**：让一个模型写代码，再让其他模型只读代码文本互相挑错。
2. **结构化拆解**：
   - 多个模型参与；
   - 审查依据主要是代码文本；
   - 不运行程序，不观察真实执行结果；
   - 以“挑出风险”为目标进行多轮互审。
3. **作用定位**：这是视频主要反对的路线；理解它为何容易产生假警报，是后续转向 TDD 与形式化验证的前提。

### 首现讲解：TDD 与真实运行验证

1. **一句话本质**：先写测试定义预期行为，再写实现让测试通过，并把程序真实运行起来验证。
2. **结构化拆解**：
   - 先写测试，把预期行为固定下来；
   - 先看到测试失败，再写实现让它通过；
   - 把真实程序启动、操作、观察结果；
   - 用真实执行结果判断边界问题。
3. **作用定位**：它对应“具体功能实现”的正路；掌握后可用可执行测试和真实运行结果替代空谈式审查。

### 首现讲解：形式化验证（含 TLA+ / Kani）

1. **一句话本质**：用数学方法穷举系统所有可能执行步序，检查设计是否满足要求。
2. **结构化拆解**：
   - 把系统抽象成状态与转移规则；
   - 写出必须成立的性质；
   - 用 TLA+ 或 Kani 穷举所有步序；
   - 先用故意改坏的验证对象跑出失败，确认工具真能抓问题。
   - TLA+ 与 Kani 是视频点名的形式化验证工具；本稿按原文将其作用概括为穷举执行步序。
3. **作用定位**：它对应“复杂架构与状态变化”的正路；掌握后可用数学检查覆盖几十步交错的死角。

## 核心要点

对应链条第 1-7 环：以下五条概括视频主线。

1. 视频反对让大模型做脱离运行环境的对抗性代码审查，认为这是根子上走偏。
2. 这类审查会报出大量误报，把干净的小改动逼成冗余补丁，却漏掉真实运行才暴露的问题。
3. 具体功能应采用先写测试、再写实现并真实运行验证的路线。
4. 复杂架构应采用大模型辅助的形式化验证，用工具穷举执行步序。
5. 质量机制应看真实故障拦截率和误报与真问题比，互审在这两项上算不过账。

## 关键细节

对应链条第 2-7 环：以下事实、数据与例子支撑主线。

- Laurent 是 Rust 编译器核心成员，现于 xAI 做 Grok。  
  **首现讲解：Rust 编译器**  
  1. **一句话本质**：Rust 编译器是把 Rust 源代码翻译成可执行程序并做静态检查的工具。  
  2. **结构化拆解**：读取 Rust 源代码；检查类型与规则；生成可执行结果；在运行前发现部分错误。  
  3. **作用定位**：本文用它说明编译器能计算程序约束，而只读代码的模型难以做到。  
  **首现讲解：xAI 与 Grok**  
  1. **一句话本质**：xAI 是人工智能公司，Grok 是其模型产品。  
  2. **结构化拆解**：xAI 是公司主体；Grok 是模型产品；二者用于说明 Laurent 的当前工作背景。  
  3. **作用定位**：提供案例人物的行业背景，增强 Pistachio 案例的可信度。

- Pistachio 工程插件包大幅砍掉对抗性代码审查，准备彻底删掉。  
  **首现讲解：Pistachio**  
  1. **一句话本质**：Pistachio 是视频提到的工程插件包。  
  2. **结构化拆解**：它是工程插件包；其中曾包含对抗性代码审查；视频称其大幅砍掉并准备彻底删除该审查。  
  3. **作用定位**：它是视频用来说明“对抗性审查走偏”的现实案例。

- 让 AI 只对着静态代码差异审查会失灵。  
  **首现讲解：静态 diff**  
  1. **一句话本质**：静态 diff 是只比较代码修改前后的文本差异，不运行程序。  
  2. **结构化拆解**：查看新增与删除的代码行；不执行程序；不读取运行状态；只能依据文本推断风险。  
  3. **作用定位**：本文用它指代对抗性审查的主要输入，说明其脱离真实运行环境。

- 失灵原因：大模型无法像编译器那样算清全局不变量，也没把程序真跑起来看一眼，只能顺着字面意思猜。  
  **首现讲解：不变量**  
  1. **一句话本质**：不变量是程序执行全程都必须成立的条件。  
  2. **结构化拆解**：它约束系统状态；需要在所有执行路径上保持；只读局部代码难以判断全局是否成立。  
  3. **作用定位**：本文用它说明对抗性审查缺少全局计算能力，因此容易误判。

- 为交差，模型会把所有看起来像风险的地方全报上来；担心缺空值判断、并发乱序，核对后发现十有八九是假警报。  
  **首现讲解：空值判断、并发乱序与死锁**  
  1. **一句话本质**：它们是运行期常见风险：值可能为空、并发执行顺序不确定、互相等待导致无法继续。  
  2. **结构化拆解**：空值判断检查可能为空的值；并发乱序指多任务执行顺序不确定；并发竞争指多方同时访问共享资源；死锁指多方互相等待资源而无法推进。  
  3. **作用定位**：本文用这些例子说明只读代码的审查容易报出大量实际不成立的警报。  
  **首现讲解：假警报**  
  1. **一句话本质**：假警报是审查报告为风险、但实际不成立的问题。  
  2. **结构化拆解**：它消耗处理成本；会拉低审查可信度；是质量指标中“每拦一个真问题要处理多少假警报”的分子。  
  3. **作用定位**：本文用它说明对抗性审查的主要代价。

- 写代码的 AI 为过关，会塞满防御性分支和冗余兜底；几个回合后 Token 多烧好几倍，十行改动膨胀成一百行。  
  **首现讲解：防御性分支与冗余兜底**  
  1. **一句话本质**：它们是为防范潜在风险而额外加入的判断逻辑和备用处理逻辑。  
  2. **结构化拆解**：防御性分支提前处理可能异常；冗余兜底在失败时提供备用路径；过度加入会增加代码体积与维护成本。  
  3. **作用定位**：本文用它们说明对抗性审查会诱导写码模型制造冗余补丁。  
  **首现讲解：Token**  
  1. **一句话本质**：Token 是大模型处理文本时的计量单位。  
  2. **结构化拆解**：输入文本按 Token 计量；输出文本也按 Token 计量；多轮互审会增加消耗。  
  3. **作用定位**：本文用它说明互审路线会显著增加模型调用成本。

- 真正一跑就会崩的界面卡死、配置漏配，几个审查模型盯着 Diff 看了半天，一个也没看出来。

- TDD 与真实运行：先写测试把预期行为定死，先看到测试跑红，再写刚好跑绿的实现；把真实程序拉起来，点一遍，看一眼；边界问题一行真实测试跑下去，三秒钟见分晓。

- 形式化验证：并发竞争、网络重连、多端同步等架构设计，出错常在几十步交错的死角；大模型适合把架构抽成状态机，交给 TLA+ 或 Kani 穷举所有步序；先在故意改坏的模型上跑红一次，证明它真能抓出死锁。  
  **首现讲解：状态机**  
  1. **一句话本质**：状态机用一组状态和转移规则描述系统行为。  
  2. **结构化拆解**：系统处于某个状态；事件触发状态转移；转移条件决定下一步；可被工具穷举检查。  
  3. **作用定位**：本文用它说明复杂架构如何被抽象后交给形式化验证工具。

- 凡是重复犯过两次的错，就按从硬到软的顺序焊死在底座里：先合成单一状态源，再用类型系统让非法状态编译不过，接着写进 TDD 测试，最后才写进文档。  
  **首现讲解：单一状态源**  
  1. **一句话本质**：单一状态源是让系统关键状态只保留一个权威来源。  
  2. **结构化拆解**：减少多副本；降低同步冲突；让读写围绕同一来源进行。  
  3. **作用定位**：本文把它列为“从硬到软”防错顺序的第一层。  
  **首现讲解：类型系统**  
  1. **一句话本质**：类型系统是程序运行前检查数据种类和操作是否合法的规则集合。  
  2. **结构化拆解**：给数据规定类型；检查操作是否匹配；让非法状态在编译阶段不通过。  
  3. **作用定位**：本文用它说明如何用编译期检查把错误挡在前面。

- 衡量质量机制有两个硬指标：第一，把真实发生过的线上故障放回去，能不能百分之百拦住；第二，每拦住一个真问题要陪它处理多少个假警报。  
  **首现讲解：线上故障**  
  1. **一句话本质**：线上故障是生产环境真实用户使用中发生的故障。  
  2. **结构化拆解**：发生在真实流量下；涉及真实配置与真实数据；可作为回归验证样本。  
  3. **作用定位**：本文用它作为检验质量机制能否拦住真实问题的标准。

- 靠大模型嘴皮子互审，这两个指标永远算不过账；只有 TDD 加形式化验证才是经得起检验的正路。

## 原文没有讲清的问题

对应链路未闭环环节：以下问题视频未展开，但值得追问。

5. 对抗性代码审查是否完全无价值，还是只能作为辅助手段，视频未给出组合使用条件。

## 原文文案

我从一开始就反对让大模型之间搞对抗性代码审查，AI 写代码只有两条正路。具体功能的实现，靠 TDD 测试驱动开发和真实运行验证，架构与复杂状态机的设计，现在大模型可以做形式化验证，对，也是正路。让一个模型写完代码再拉两三个大模型对着静态 diff 挑刺，从根子上就是走偏了。前两天，Rust 编译器核心成员，现在在 xAI 做 Grok 的 Laurent 发了条推文，说的正是这件事。它的工程插件包 Pistachio 里大幅砍掉了对抗性代码审查，准备彻底删掉，因为让 AI 脱离运行环境，对着静态代码空谈审查，只会扎进吹毛求疵的命名细节或者编造一堆过度设计，为什么对抗性审查会失灵？因为大模型没法像编译器那样算清全局不变量，也没把程序真跑起来看一眼，只能顺着字面意思猜。为了交差，它把所有看起来像风险的地方全报上来。一会儿担心缺个空值判断，一会儿怀疑并发会乱序，去核对就会发现十有八九是假警报。更要命的是，写代码的 AI，为了过关，会往代码里塞满防御性分支和冗余兜底，几个回合下来，Token 多烧了好几倍，原本干净的十行改动膨胀成一百行，没人敢碰的补丁。而真正一跑就会崩的界面卡死、配置漏配，几个审查模型盯着 Diff 看了半天，一个也没看出来，互审吵架的 Token 省下来，回到两条正路上，这笔账才算得过来。第一条正路是 TDD 与真实运行，先写测试把预期行为定死，先看到测试跑红，再写刚好跑绿的实现，把真实程序拉起来，点一遍，看一眼，很多争论不休的边界问题，一行真实测试跑下去，三秒钟就见分晓。第二条正路是用大模型做形式化验证，并发竞争、网络重连、多端同步这些架构设计，出错往往在几十步交错的死角里。现在大模型非常适合把架构抽成状态机，交给 TLA+ 或 Kani 去穷举所有步序，只要先在故意改坏的模型上跑红一次，证明它真能抓出死锁，以后每次改架构就都有了数学兜底，凡是重复犯过两次的错，就按从硬到软的顺序，焊死在底座里。先合成单一状态源，再用类型系统让非法状态编译不过，接着写进 TDD 测试，最后才写进文档。衡量一套质量机制有两个硬指标，第一把真实发生过的线上故障放回去能不能百分之百拦住。第二，每拦住一个真问题要陪它处理多少个假警报，靠大模型嘴皮子互审，这两个指标永远算不过账，只有 TDD 加形式化验证才是经得起检验的正路。谢谢大家，我们下期见！
