# AI Agent 面试/简历知识点整理复盘（2）

## 精华版

视频围绕 AI Agent 面试/简历项目复盘了六类知识点：Skill 用 prompt 和工具组成、按需暴露工具描述以节省上下文；A2UI 把前端操作类工具移到前端并按页面加载/卸载；Voice Agent 可作为差异化项目，但级联模式存在误差传递和串行延迟，端到端是方向但未普及；RAG 项目要按规模、并发、过滤和运维成本选数据库与 Embedding/Rerank，不要默认 LangChain+Milvus；RAG 全链路延迟约 0.5–1 秒，更适合长推理文档任务；Agent 验证与发布要用 LLM-as-a-Judge、校准、压力测试、记忆 benchmark、灰度发布和固定 Harness 横向换模型验证。整体结论是：项目选型要匹配真实规模与场景，避免简历项目同质化和数据虚高。

## 整体逻辑链条梳理

1. **面试项目同质化 → 需要差异化与真实选型**：文本 Agent 项目太卷，RAG 技术栈又常见固定组合，因此要理解各模块边界和规模匹配。
2. **工具数量膨胀 → Skill 渐进暴露工具信息**：Skill 由 prompt 和工具组成，只在需要时暴露工具描述，节省上下文。
3. **前端操作类工具耦合麻烦 → A2UI 前端化**：把工具从后端移到前端，按页面加载/卸载，但切页卸载工具会影响长链任务。
4. **文本 Agent 太卷 → Voice Agent 成为差异化方向**：级联模式易误差传递、串行延迟高；半级联和端到端是改进方向。
5. **RAG 是简历常见项目 → 按规模选型并理解全链路**：数据库、Embedding、召回、Rerank、Parse、Chunking 各有取舍，延迟逐层叠加。
6. **Agent 上线前要验证与发布 → LLM-as-a-Judge、压力测试、记忆测试、灰度、Harness 对比**：验证模型和发布流程已成为面试必问。
7. **收束结论 → 选型匹配规模与场景，避免虚高和同质化**：每一环都指向“项目要真实、可解释、可验证”。

## 一句话结论

AI Agent 面试/简历项目应按真实规模和场景做选型，理解 Skill、A2UI、Voice Agent、RAG 与验证发布各环节的边界和取舍，避免同质化与数据虚高。

## 核心要点

1. **（对应链条第 2 环）** Skill 由 prompt 和工具组成，工具常挂后台，只在需要时暴露具体描述和变量设置，从而节省上下文。
2. **（对应链条第 3 环）** A2UI 把工具从后端移到前端，按页面加载和卸载，适合前端操作类工具，但切页卸载工具与长链任务冲突。
3. **（对应链条第 4 环）** Voice Agent 可作为差异化项目方向，级联模式存在误差逐级放大和串行延迟问题，端到端模型是方向但尚未普及。
4. **（对应链条第 5 环）** RAG 数据库选型要看规模、并发、过滤和运维成本，不要默认 LangChain+Milvus，绝大多数公司文档量远小于 Milvus 的优势区间。
5. **（对应链条第 5 环）** RAG 流程包括 Parse、Chunking、Embedding、召回、Rerank，全链路延迟约 0.5–1 秒，更适合长推理文档任务。
6. **（对应链条第 6 环）** Agent 验证与发布要用 LLM-as-a-Judge、校准、压力测试、记忆 benchmark、灰度发布和固定 Harness 横向换模型验证。

## 关键细节

- **Skill**：组成是 prompt 和工具；工具常挂后台，Skill 提供工具描述和变量设置；工具数量可达几百几千，全部放入 system prompt 会受注意力机制容量限制；Skill 按需加载，节省上下文。
- **Skill 与 MCP**：视频提到部分纯文本类 prompt 类 Skill 可能被淘汰，但具体项目的 Skill 仍会保留；例如 git clone template 后自动加载 Skill，帮助更快搭建 template。
- **A2UI**：把工具从后端移动到前端；按页面加载部分工具，切页卸载；支持 Agent 在网页上原地创建元素、为每个用户定制操作界面；缺点是切页卸载工具时 KV 不会回掉，因此与长链任务冲突。
- **Voice Agent 级联模式**：类似自动客服的多模块串行流程；最后输出的 reward 无法传回最初模块；第一模块小错误会被逐级放大；每个模块都有责任，难以单独修正；需要两到三个独立模型，串行线性依赖导致推理延迟难降。
- **语音协议与模块**：常用 WebRTC 做实时音视频通信，通常基于 UDP；级联模式不是 VoIP，丢少量数据可接受；语音转文本可拆为 VAD（检测是否说话）和 ASR（识别具体内容）；半级联可把 ASR 与 LM 合为 AudioLM。
- **ASR 方案**：CTC 匹配帧和文字，传统、低耗、低延迟；AED 用 Encoder-Decoder，先把语音投射到 Latent Space；自回归 ASR 接近 AudioLM，但仍是语音转文字。
- **TTS 方案**：自回归常用 LM 架构，推理较强；非自回归走扩散模型，可并行生成音频、延迟低，但长文本和情感表达较弱。
- **端到端语音**：视频提到天工 Audio 3.0、豆包、CosyVoice、OpenAI 等；延迟普遍约 250–500ms；阿里有特化音频协议 AOQ，除阿里外少有人支持；端到端仍支持文本 prompt，上下文多以文本保存，音频 token 较贵。
- **RAG 数据库**：Milvus 适合几十亿向量和低延迟，但几十亿向量需要多卡、跑很久；50 万向量下 Milvus 无明显优势；1 亿向量约等于 800–1000 万份文档，绝大多数公司文档库没有这个体量。
- **PGVector**：PostgreSQL 插件，共享数据库存储，可能影响主库搜索速度；QPS 约 100 以下、10 万条以下向量可放心用；50–100 万条也能用；PGVector 本身不是分布式。
- **Qdrant/Weaviate/Pinecone**：定位约百万到一亿向量；Qdrant 开源；Pinecone 是 SaaS，上手简单但体量变大后迁移麻烦；三者更新频繁，选型差异不大。
- **Milvus 与 Elasticsearch**：Milvus 支持几亿到几十亿级、高 QPS、原生分布式；2024 年 Milvus 已支持 BM25，Elasticsearch 也支持 Dense，旧教程中“Milvus+ES 分工”已过时；很多企业会复用原有 ES 流程。
- **Embedding**：BGE 布局早，常见 BGE1.5、BGE3；早期需关注中英文语言匹配，现在新模型多语言支持较好；近年 Embedding 参数量向 10.5B 发展，部分厂商发 32B 以上；千问 Embedding 刷榜较强，实际与 BGE 同参数量差异不显著；多模态向量生成仍偏概念化，效果一般。
- **召回与 Rerank**：BM25 做精准匹配，BGE 做模糊向量检索；两路结果用 RRF 合并排名，再用 Rerank 提升 Precision；Rerank 直接比较 Query 与原始数据，计算量更高但打分更精细；通常取 5–10 个文档给 LM。
- **RAG 延迟**：每部分级联，延迟逐层叠加；瓶颈主要在召回和 Rerank；总延迟约 0.5–1 秒，因此不适合快速回复，更适合长推理任务。
- **Parse**：把 PDF、PPT、Markdown、Doc 等转统一文本；单一文件常用 Unstructured，复杂 PDF 可用 Docling；复杂 PDF 也可用带视觉功能的 LLM 直接读取，但成本比 OCR 高很多。
- **Chunking**：固定大小切分面试常问但少用；结构切分和语义切分常组合；语义切分按相邻句子/段落相似度选切割点；变种包括 Overlap 保留上下文、父子文档用较小句子建 Embedding 再找回完整文档；常见 2–3 次索引，部分设计 6 层以上。
- **RAG 适用场景**：强项在文档类搜索；口语、明确命名实体任务表现一般；个人本地 Agent 通常用普通本地向量搜索即可；公司内部 Agent 文档库仍必要；Agent 的 RAG 通常作为工具，由 Agent 自己选择是否使用，强依赖 RAG 的模式基本被淘汰。
- **LLM-as-a-Judge**：打分要写清 1–5 分描述；不同标准要隔离，避免正确性和安全性互相串扰；不要让 Agent 对两个目标同时打高低分；Judge 尽量不要用同一家模型；Judge 有 Noise 和漂移，需要校准。
- **校准与 Kappa**：准备人类数据集，计算加权 Kappa，接近 1 认为 Judge 与人类打分相似；变体有 Cohen’s Kappa、Fleiss Kappa；校准集 100–200 条样本通常足够；要避免偷偷改版本的模型厂商。
- **偏见与压力测试**：LLM-as-a-Judge 有位置偏见、上下文偏见，可通过隐藏身份标识降低但不能完全解决；标准压力测试先测单用户基准，再成倍增加请求看指标是否线性增长；暴力压测很花钱。
- **记忆系统测试**：LoCoMo 等 benchmark 有变种；常见问题是容量虚高，测试从空记忆开始；多模型切换下难以判断记忆有效性；外部系统更新记忆使测试更困难；Mem0 常被调侃，但实际公司使用不多。
- **灰度发布**：通常拿 10% 用户测试，用户不知道版本；关注成功率、模型切换频率、模型升级频率、打断频率等；通过后逐步到 100%；可用 Nginx 热加载分配权重或云平台流量控制。
- **Harness 验证**：固定 Harness 换多个模型，确认提升来自 Harness 而不是模型；例如换 DeepSeek、加 Skill、加 GT、加 Cloud 做横向对比，看整体是否提升。
