# 视频学习笔记：模型生成任务计划

## 精华版

本课解决手工编写任务计划费事的问题。流程是：用户需求进入规划组件；规划组件组织固定规则和用户消息，调用外部生成服务；服务返回结构化文本；程序解析文本，若被代码围栏包裹则先提取；随后把数据转成任务计划对象，检查字段类型、依赖关系和工具是否存在；全部通过才返回合法任务计划，否则抛异常终止。测试用真实服务跑演示脚本，成功生成合法计划；下节课把相关部分深度整合。视频留两个问题：规划组件的主要职责；结构化文本合法但引用不存在工具时怎么办。

## 整体逻辑链条梳理

1. 用户自然语言需求是输入，需要被转换为机器可执行的任务计划；因为后续执行依赖明确步骤和工具，所以先由规划组件承接需求。
2. 规划组件组织固定规则和用户消息，调用外部生成服务；因为模型输出需要约束，所以系统提示中要传入工具描述和输出格式规则。
3. 服务返回结构化文本，程序必须解析成可处理的数据；因为模型可能把结构化文本包在代码围栏里，所以解析要带兜底提取。
4. 数据要转成任务计划对象并校验协议字段类型和依赖关系；因为结构合法不代表步骤顺序可执行，所以协议校验之后还要做依赖校验。
5. 计划引用的工具必须在工具清单中存在；因为模型可能生成不存在的工具，所以要做工具存在性检查。
6. 全部通过返回合法任务计划，任一失败抛异常终止；测试用真实服务验证流程，下节课再与已有部分深度整合。开放问题集中在协议细节、依赖规则和工具不存在后的处理策略。

## 关键名词首现讲解

对应链条第 2-5 环。

1. **TaskPlan（任务计划协议）与 TaskPlanner（任务计划生成器）**
   - 一句话本质：TaskPlan 是任务计划的数据协议；TaskPlanner 是根据用户需求生成并校验该协议的组件。
   - 结构化拆解：TaskPlan 约定任务步骤、字段类型、依赖关系和工具调用字符串；TaskPlanner 包含异常类、构造函数、消息构建函数、结构化文本解析函数和入口函数；工作方式是构建消息、调用模型、解析结果、执行校验、返回合法计划。
   - 作用定位：它把用户需求转成后续可执行、可校验的计划对象，是本节课自动生成任务计划的核心组件。

2. **LLM（大模型）、System Prompt、SystemMessage、UserMessage、Response.content**
   - 一句话本质：LLM 是接收消息列表并返回文本的生成服务；System Prompt 是给模型的固定规则文本；SystemMessage 和 UserMessage 是承载规则与需求的消息角色；Response.content 是返回对象中的文本内容。
   - 结构化拆解：TaskPlanner 构造函数保存 LLM；buildMessages 生成一条 SystemMessage 和一条 UserMessage；SystemMessage 内含工具描述和输出格式规则；入口函数调用 LLM 后用 getattr 取 Response 的 content。
   - 作用定位：这些部分决定模型收到什么约束、返回什么文本，是自动生成计划的关键输入输出通道。

3. **JSON、json.dumps、JSON 解析、Markdown 代码块、正则**
   - 一句话本质：JSON 是一种结构化文本格式；json.dumps 把对象转成 JSON 字符串；JSON 解析把 JSON 字符串转成程序数据；正则用于按模式提取文本；Markdown 代码块是用反引号包裹的文本块。
   - 结构化拆解：buildMessages 用 json.dumps 把工具描述转成 JSON 串；解析函数先去空白，再直接解析；直接解析失败时，用正则去掉 Markdown 代码块并取中间代码再解析；仍失败则抛异常。
   - 作用定位：它们负责把模型返回的文本稳定转成程序可校验的数据，是流程中的解析环节。

4. **toolRegistry（工具注册表）、工具 schema、白名单检查、工具验证、幻觉**
   - 一句话本质：toolRegistry 保存所有可用工具及其描述；工具 schema 是工具的描述结构；白名单检查和工具验证是检查计划引用的工具是否存在；幻觉指模型生成不存在的内容。
   - 结构化拆解：buildMessages 通过 json.dumps 取 toolRegistry 中所有工具的 schema；入口校验计划中的工具调用字符串是否在 toolRegistry 中存在；不存在说明模型出现幻觉，要抛异常。
   - 作用定位：它防止模型编造不存在的工具，保证生成计划只能使用系统允许的工具。

5. **TaskPlannerException、异常、校验、依赖校验**
   - 一句话本质：异常是程序失败时抛出的错误信号；校验是按规则检查数据是否合法；TaskPlannerException 是任务计划生成或校验失败时使用的异常类。
   - 结构化拆解：TaskPlannerException 继承 Exception；校验包括把 JSON 转成 TaskPlan 后检查协议和字段类型、检查依赖关系、检查工具是否存在；任一不合法就抛出异常终止计划。
   - 作用定位：它让失败明确中断，避免不合法的任务计划继续流入后续执行环节。

6. **Python 实现相关：构造函数、成员变量、静态函数、getattr、入口函数、demo**
   - 一句话本质：这些是代码组织与运行方式；构造函数初始化对象，成员变量保存对象状态，静态函数不依赖实例，getattr 按属性名取对象属性，入口函数串联主流程，demo 是演示脚本。
   - 结构化拆解：构造函数保存 LLM 和 toolRegistry 为成员变量；结构化文本解析写成静态函数；入口函数依次构建消息、调用模型、取 content、解析、校验、返回；taskplanner_demo 用于用真实模型跑通流程。
   - 作用定位：理解这些代码结构，才能读懂 TaskPlanner 的实现路径和测试方式。

## 一句话结论

对应链条第 6 环。本课让 TaskPlanner 用 LLM 根据用户需求生成 JSON 任务计划，经解析、TaskPlan 校验和工具存在性检查后返回合法 TaskPlan，失败则抛 TaskPlannerException。

## 核心要点

对应链条第 1-5 环。

1. 用户自然语言需求先交给 TaskPlanner，由它构建 SystemMessage 和 UserMessage 调用 LLM。
2. LLM 返回 JSON 后，解析函数先去空白并直接解析，失败则用正则去掉 Markdown 代码块再解析，仍失败抛异常。
3. 入口函数检查 content 非空且为字符串，再解析 JSON、转 TaskPlan，并校验协议字段类型和依赖关系。
4. 工具验证检查计划中的工具调用字符串是否存在于 toolRegistry，防止模型幻觉。
5. 测试用真实 LLM 在 taskplanner_demo 中执行，成功生成合法 TaskPlan；下节课做深度整合。

## 关键细节

对应链条第 2-6 环。

- 在 Agent 目录下创建 TaskPlanner 文件。
- 文件中有两个类：TaskPlannerException 继承 Exception；TaskPlanner 用于根据用户需求生成经过校验的任务计划。
- TaskPlanner 构造函数有两个参数：LLM 和 toolRegistry，并保存为成员变量。
- buildMessages 接收自然语言需求，返回消息列表：先用 json.dumps 取 toolRegistry 中所有工具的 schema 转为 JSON 串，再构造 System Prompt 并传入工具 JSON schema 和输出格式规则，最后返回 SystemMessage 和 UserMessage 两条消息。
