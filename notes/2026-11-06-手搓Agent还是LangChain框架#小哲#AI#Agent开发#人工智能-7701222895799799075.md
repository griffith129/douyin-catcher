# 手搓 Agent 还是 LangChain 框架——学习笔记

## 精华版

| 术语 | 一句话本质 | 结构化拆解 | 作用定位 |
|---|---|---|---|
| Agent | 能按目标调用工具并推进任务执行的软件实体 | 组成：目标、可调用工具、执行步骤、状态记录；机制：接收任务→拆步骤→调用工具→根据结果继续或结束 | 本文讨论的开发对象 |
| LangChain | 用于构建 Agent 和任务流程的开发框架 | 组成：模型调用接口、工具接入、流程组合、状态保存等通用能力；机制：用统一接口组织多步骤调用 | 本文的框架方案 |
| C端 | 面向普通消费者直接使用的产品场景 | 组成：用户直接使用产品功能；机制：用户对速度、稳定、报错敏感，要求快和稳 | 判断手搓适用性的核心场景 |
| 长链路 | 任务需要多步骤、多轮调用和连续推理才能完成 | 组成：多层拆解、多次调用、状态传递；机制：步骤多导致流程和状态管理复杂 | 框架适用的边界场景 |
| 手搓 | 不依赖现成 Agent 框架，自行编写任务流程和调用逻辑 | 组成：自主定义链路、处理输入输出、错误定位；机制：减少封装层，按业务定制 | 轻量高频场景的候选方案 |

视频结论：选择手搓 Agent 还是 LangChain，不是技术水平高低，而是场景与用户体验匹配。LangChain 不是不能用，但轻量场景硬套会带来用不到的通用功能、拖慢响应并提高出错风险；C端需求清晰、链路简洁时，手搓更利于快和稳、自主可控；超长任务链、多层拆解和复杂状态管理等场景，框架更合适。取舍是按需匹配：高频轻量功能手动打磨，少数复杂场景引入框架。面试考察的是懂框架短板、理解业务诉求、选出适配用户体验的方案。

## 整体逻辑链条梳理

1. 面试题表面问技术选型，实际问业务权衡；成立原因是线上用户体验是最终约束；衔接：先打破“框架=偷懒、手搓=技术高”的误区。
2. 框架并非不能用，但轻场景强行套用会带来冗余功能、延迟和异常；成立原因是框架为通用场景设计；衔接：引出必须判断具体场景。
3. C端核心要求是快和稳，需求清晰、链路简洁时适合手搓；成立原因是手搓链路精简、可控、问题定位快；衔接：但手搓不是万能。
4. 长链路复杂任务需要多层拆解和复杂记忆管理，适合引入框架；成立原因是重复造轮子成本高；衔接：形成按需匹配的取舍逻辑。
5. 取舍策略是高频轻量功能手动打磨，少数复杂场景引入 LangChain；成立原因是围绕用户体验与效率权衡；衔接：落到面试高分答案。
6. 面试真正考察三点：懂框架短板、理解业务诉求、选出适配用户体验的方案；成立原因是只懂技术优缺点不够；收束全文。

## 一句话结论

（对应链条第5-6环）视频认为手搓 Agent 还是用 LangChain 不是技术水平之争，而是按业务场景和用户体验做取舍：轻量高频 C端场景优先手搓，长链路复杂任务按需引入 LangChain。

## 核心要点

- 框架与手搓的选择不等于技术高低，关键看场景是否匹配。（对应链条第1环）
- 轻量场景硬套 LangChain 会增加用不到的通用功能、拖慢响应并提高出错风险。（对应链条第2环）
- C端产品核心是快和稳，需求清晰、链路简洁时手搓更利于速度和自主可控。（对应链条第3环）
- LangChain 的优势在超长任务链、多层拆解和复杂状态管理等复杂场景。（对应链条第4环）
- 取舍策略是按需匹配：高频轻量功能手动打磨，少数复杂场景引入框架。（对应链条第5环）
- 面试真正考察的是理解框架短板、业务诉求，并选出适配用户体验的方案。（对应链条第6环）

## 关键细节

（对应链条第2-5环）

- 框架内置大量通用能力与多层封装（冗余封装：指框架为通用场景提供的多层抽象和内置功能；组成包括流程组合、状态保存等；机制是轻场景用不到却仍要经过这些层；作用定位是解释框架负担），开发初期省事，但在中小规模 AI 功能中反而成额外负担。
- 上线后直接问题是响应延迟（响应延迟是用户发出请求到系统返回结果的时间；受调用层数、封装开销、模型计算等影响；作用定位是 C端体验关键指标）升高，并出现不可控异常（异常是运行中出现的非预期错误；来源包括框架内部和外部调用；作用定位是框架误用风险）；用户感知为卡顿、容易报错。
- 手搓优势：链路精简、无冗余封装、响应更快、全程自主可控、每段逻辑自定义、问题定位修复快、不受框架黑盒（黑盒指内部实现不透明、难以直接观察和修改的封装；机制是只暴露接口；作用定位是手搓强调自主可控的对照点）干扰。
- 框架适用边界：超长任务链、多层拆解与复杂记忆管理（记忆管理指在多步骤任务中保存、读取和更新任务状态；组成包括状态存储、读取、更新；机制是让后续步骤使用前文信息；作用定位是复杂长链路任务的支撑能力）。
- 取舍策略：高频轻量化用户功能全靠手动打磨；仅在少数长链路嵌套、需大量复杂推理的特殊场景中引入 LangChain。
- 总结原则：轻场景不堆砌重型工具，复杂场景不重复书写逻辑，所有决策围绕用户体验与效率权衡。
- 原文没有给出具体延迟数值、异常率、项目规模等数据。

## 原文文案

我先看这个问题，为什么选择手搓 Agent 而不是 LangChain 这种框架？如果回答“手搓更灵活，框架太重了”，那基本只能回家等通知吧。这道题看似问技术选型，实则考察你能否结合业务场景做权衡，有没有忽视线上真实用户体验。大多数候选人的回答都差不多：框架封装太死板，手搓的自由度更高。听着好像有道理，但全是网上套话，一被问到业务就扛不住。我是小哲，点赞收藏加关注，我们马上开始。想系统学习 Agent 开发的同学，可以查看橱窗哦。很多人其实没切中要害，LangChain 并非不能用，但在不少 C 端场景强行套用框架，反倒得不偿失。盲目引入框架会带来很多项目根本用不到的冗余功能，拉高响应延迟，还极易引发不可控的异常。但也不能不分场景都硬着头皮去手搓，一旦碰到长链路复杂任务，又得重复造轮子，耗费大量时间。单纯照搬教程跟风选方案，缺少独立判断，做项目就全靠运气。面试官抛出这道题，从来不是考察你会不会调用框架、能不能写代码，核心其实在于三点：清楚框架的短板，理解业务核心诉求，能选出适配用户体验的方案，这才是拿到高分的关键。我的理解是核心在于三层逻辑。首先，打破常规认知误区，选择框架还是手工设计，跟技术水平高低无关，关键在于场景是否匹配。不是用框架就代表偷懒，手搓也不等同于技术高超。很多人之所以踩坑，是不管业务大小，一上来就硬套现成的 LangChain 框架。内置的大量通用能力与多层封装，在开发初期看着挺省事，但到了中小规模的 AI 功能中反而成了额外负担。上线后最直接的问题就是延迟升高，还经常出现莫名其妙的异常。用户感受不到智能，只会觉得产品卡顿、容易报错。第二层要讲清楚，手搓 Agent 适合什么场景。做 C 端产品最核心的要求无非两点：快和稳。许多日常业务场景的需求清晰明确，链路简洁，无需复杂的多轮调用，框架自带的高阶能力完全用不上。在此类场景下，手搓 Agent 的优势尤为明显：链路精简，没有冗余封装，响应更快，全程自主可控，每段逻辑都由自己定义，出现问题能迅速定位修复，不受框架黑盒和逻辑的干扰，正好契合 C 端用户对流畅稳定的严苛要求。手搓手动处理，减少不必要的冗余负担。第三层要明确框架的适用边界，体现全局思维。我选择手动操作并非排斥使用 LangChain，也不是全盘否定框架。我很清楚它的优势，擅长应对超长任务链、多层拆解与复杂记忆管理。因此我的取舍逻辑是按需匹配：高频轻量化的用户功能全靠手动打磨，确保流畅稳定的基础体验；仅在少数长链路嵌套、需大量复杂推理的特殊场景中才引入 LangChain 来拉高功效。简而言之，轻场景不堆砌重型工具，复杂场景不重复书写逻辑，所有决策皆为围绕用户体验与效率来权衡，这才是面试官真正想听到的答案。只知道技术优缺点的充其量只是写代码的人，真正做过线上项目的人才懂得结合场景与用户体验做取舍。
