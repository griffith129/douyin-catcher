# 任务计划接入Runtime 手搓Agent 进阶第六课 #AI #agent #RAG #Skill #智能体

## 精华版

这条视频解决的是：任务规划与任务执行此前各自完成，但没有被同一个入口串起来。视频给出完整链路：用户请求进入统一入口 → 生成任务计划 → 封装并校验计划 → 转成普通任务并调度执行 → 执行中产生事件并收集结果 → 把结果与原始请求交给模型生成最终回答 → 将过程与结果发送到前端。测试验证了并行任务按完成先后返回，依赖任务在依赖完成后执行。前端展示与通信处理留到下一课。

## 整体逻辑链条梳理

1. 起点：规划组件与执行组件已存在但未串联，所以需要统一入口把二者接起来；统一入口负责组织后续所有调用。
2. 请求进入统一入口后，先由规划组件生成计划；因为执行前必须先知道要做什么。
3. 计划需要被封装、校验、转换成可执行任务；因为规划结果不能直接等同于可调度任务。
4. 调度器执行普通任务并调用工具，过程中产生事件；事件被收集，因为执行过程和结果需要被记录与展示。
5. 若没有收集到结果则报错；若有结果，则把结果与原始请求交给最终回答生成器；因为执行器只调用工具，不产出最终回答。
6. 测试验证并行与依赖行为；因为调度行为只能通过实际返回顺序观察。
7. 前端展示与通信处理留到下一课；因为本课只把事件打印到控制台。

## 术语首现讲解

### Agent Runtime

- 一句话本质：它是组织并驱动任务规划与任务执行的运行时容器。
- 结构化拆解：
  - 解决什么问题：把规划组件与执行组件从“各自存在”变成“同一入口下串联调用”。
  - 关键机制：持有任务规划器与任务执行器；接收用户请求；按“规划 → 执行 → 收集事件 → 检查结果 → 生成最终回答 → 发送前端”组织调用。
- 作用定位：它是本文档的总调度入口，理解它才能看清规划器与执行器如何被串成完整链路。

### Task Planner、PlannerTask、Task DA、Task Convert、Task Scheduler

- 一句话本质：这组组件负责把用户需求变成可执行任务并调度执行。
- 结构化拆解：
  - Task Planner：负责生成任务规划，并把规划封装为 PlannerTask。
  - PlannerTask：任务规划结果的数据封装，存放在 Task Planner 中，供后续校验与转换。
  - Task DA：文字稿原文名称，具体全称未展开；在本流程中负责校验 PlannerTask。
  - Task Convert：把 PlannerTask 转换成普通 Task。
  - Task Scheduler：接收普通 Task 并组织执行。
- 作用定位：它们构成“规划数据 → 校验 → 转换 → 调度执行”的中间链路，是规划器与执行器之间的连接段。

### Task Executor、Runtime Event

- 一句话本质：执行器执行普通任务并产生过程事件。
- 结构化拆解：
  - Task Executor：调用执行器，遍历返回的 Event，并收集执行结果。
  - Runtime Event：调用工具过程中产生的事件；被 Runtime 收集、保存，并用于发送前端。
  - 关键机制：执行过程产生事件；Runtime 遍历收集；结果用于检查与展示。
- 作用定位：它们承担执行段与过程可观测职责，使 Runtime 能拿到任务执行结果并向前端传递过程信息。

### 大模型、Messages、ModelStart、Final Answer、json.dumps

- 一句话本质：这组内容负责生成任务规划或最终回答，并封装调用所需数据。
- 结构化拆解：
  - 大模型：Task Planner 调用它生成任务规划；Runtime 最后也调用它生成最终回答。
  - Messages：交给大模型的消息封装，包含执行结果与用户请求；原文未展开具体字段。
  - ModelStart：大模型开始执行前发送的标记/事件，用于说明大模型开始执行。
  - Final Answer：大模型返回的最终回答结果；Response 的 content 有内容时返回，否则给出失败提示。
  - json.dumps：把数据对象转成 JSON 格式字符串，用于处理执行结果。
- 作用定位：它们补上“执行器只调用工具、不生成最终回答”的缺口，使链路以最终回答收尾。

### async 函数

- 一句话本质：函数声明为可异步执行，调用后可在等待其他操作完成时继续处理。
- 结构化拆解：
  - 解决什么问题：组织多步调用时不因等待而阻塞整体流程。
  - 关键机制：函数可包含等待步骤；Runtime 的成员函数用 async 声明；参数为用户请求。
- 作用定位：它是 Runtime 接收用户请求并组织多步调用的函数形式。

### API、SSE

- 一句话本质：API 是系统间按约定交换请求与响应的接口；SSE 是服务器向客户端持续推送事件的通信方式。
- 结构化拆解：
  - API：定义调用方式，处理请求与响应；视频只提出“API 和 SSE 如何处理”，未展开。
  - SSE：服务器到客户端的单向事件推送，适合事件流；视频只提出，未展开。
- 作用定位：它们是下一课前端展示 Runtime Event 时的通信相关开放点。

### RuntimeDemo、runTaskPlan

- 一句话本质：它们是测试代码中的示例入口类与触发方法。
- 结构化拆解：
  - RuntimeDemo：测试中创建 AgentRuntime 的示例类。
  - runTaskPlan：用于发起任务计划执行的方法。
  - 关键机制：发送请求；每次返回 Event 打印到控制台。
- 作用定位：用于验证 Runtime 串联规划与执行后的实际行为。

## 一句话结论

视频给出把 Task Planner 与 Task Executor 接入 Agent Runtime 的完整链路：先规划，再校验、转换与调度执行，收集 Runtime Event，最后用大模型生成最终回答并发送前端。

## 核心要点

1. 上节课已有任务规划器和执行器，但未串联；本节课在 Agent Runtime 中构造并调用二者。
2. Runtime 的 async 成员函数按顺序执行：Task Planner.plan 生成 PlannerTask → Task Executor 执行并收集 Event → 检查结果 → 封装 Messages 交大模型生成最终回答。
3. 规划链路包含 PlannerTask 封装、Task DA 校验、Task Convert 转普通 Task、Task Scheduler 执行。
4. 任务执行器只调用工具，不生成最终回答，因此 Runtime 必须把执行结果与用户请求交给大模型补最终回答。
5. 测试中 getCurrentTime 先于 getWeatherNow 返回，说明并行任务按完成先后返回；依赖 T1/T2 的第三个任务在依赖完成后执行。
6. API 与 SSE 的前端处理未在本课展开，下节课计划把 Runtime Event 发到前端。
