# AI Agent 面试/简历知识点整理复盘（1）

# AI Agent 面试/简历知识点整理复盘（1）学习笔记

## 精华版

这篇复盘按面试与简历知识点串联 Agent 开发主线：开头指令段用于规定任务执行方式，但长上下文下模型不保证完整遵守，弱模型更明显，强模型上有效的提示词也不能直接迁移。上下文变长后需要压缩，摘要、索引、截断是基本套路，难点在压缩时机与推理缓存重建成本的平衡。长期记忆应聚焦跨会话持久化，最低要支持增删改查，并处理遗忘、二次处理、评测、延迟、召回、时间有效性、用户与子任务隔离、工具记忆串扰和无证据记忆。通用与特化方案要能解释业务解耦和成本理由；框架选择要看生态、重量和锁定风险。推理缓存分 KV Cache、Prompt Cache、Application Cache 三层，模型选型要看 Dense/MoE、量化精度和服务指标。工具调用要区分 Function Call 与 MCP，并做 schema 校验、重试、限流、退避、抖动和幂等。Checkpoint 与 Router 是工程化支撑，前者要解决存档加载 IO，后者要做意图识别和模型分发，并权衡切换模型导致的缓存损失。整体结论是：多数问题没有银弹，需要按场景做权衡和兜底。

## 整体逻辑链条梳理

1. **开头指令段决定任务执行方式，但长上下文下遵守不稳定**：模型通过注意力读取上下文，注意力不保证覆盖所有细节，弱模型和稀疏化优化会放大失效；因此不能把可靠性全押在提示词上。
2. **上下文膨胀后必须压缩，压缩又与推理缓存成本冲突**：摘要、索引、截断是基本套路；压缩时机会影响效果，压缩动作会使缓存失效并触发重新预填，所以要用阈值和压缩幅度做平衡。
3. **短期状态多由上下文处理，长期记忆要单独建设**：长期记忆需要增删改查、遗忘、检索、评测和隔离；记忆延迟、召回、串扰和证据匹配决定它是否可用。
4. **Agent 方案选择要解释业务与成本**：通用方案调用多、成本高；特化方案可解耦提示词、技能和工具，并用便宜模型分担任务；框架选择还要看生态和锁定风险。
5. **推理性能由缓存分层和模型结构共同决定**：KV Cache、Prompt Cache、Application Cache 分属不同层；Dense/MoE、FP8/FP4/FP2 量化和 TTFT/TPS/TPM/RPM 指标影响体验与容量。
6. **工具调用需要接口规范与可靠性治理**：Function Call 是模型输出工具调用请求，MCP 是工具接入规范；调用失败要 schema 校验、重试、限流、退避、抖动和幂等。
7. **工程化支撑收束到存档与路由**：Checkpoint 解决上下文存档与加载 IO，Router 解决意图识别与模型分发；两者都要在一致性、延迟和缓存成本间权衡。

## 一句话结论

对应链条总纲：这篇复盘把 Agent 开发中的提示词、上下文压缩、长期记忆、缓存、模型选型、工具调用、框架与工程化支撑串成一条面试知识链，核心结论是多数环节没有银弹，必须按场景做权衡、隔离和兜底。

## 核心要点

1. 开头指令段能约束任务形式，但长上下文下模型不保证完整遵守，弱模型更明显，强模型上有效的提示词不能直接迁移。
2. 上下文变长后需要压缩，摘要、索引、截断是基本套路，关键难点是压缩时机与推理缓存重建成本的平衡。
3. 长期记忆应聚焦跨会话持久化，至少支持增删改查，并处理遗忘、二次处理、评测、延迟、召回、时间有效性、隔离、工具记忆串扰和无证据记忆。
4. 通用与特化方案各有业务解耦和成本理由，特化方案可用便宜模型分担任务以降低成本。
5. 推理缓存分层，模型选型要看 Dense/MoE、量化精度和服务指标，不能只看总参数量。
6. 工具调用要区分 Function Call 与 MCP，并做 schema 校验、重试、限流、退避、抖动和幂等；Checkpoint 与 Router 是工程化支撑，均需权衡。

## 关键细节

对应链条第 1 环：开头指令段与长上下文遵守。

**Agent（智能体）快速上手讲解**
- 一句话本质：Agent 是围绕目标组织模型、外部工具和运行状态来完成任务的软件系统。
- 结构化拆解：由目标输入、任务分解、外部能力选择、结果回收、失败处理等部分组成；关键机制包括按上下文生成决策、调用工具、把结果写回上下文、循环推进任务。
- 作用定位：本文所有主题都围绕 Agent 开发与面试知识点；掌握它后可把提示词、记忆、缓存、工具和框架放到同一系统视角下权衡。

**System Prompt（系统提示词）快速上手讲解**
- 一句话本质：System Prompt 是放在对话上下文开头、用于规定任务执行方式的指令文本。
- 结构化拆解：可包含角色定义、工具说明、规则约束、格式规范；由模型在生成时读取；长上下文下不保证每个细节都被关注；效果受模型能力和上下文长度影响。
- 作用定位：是 Agent 行为约束的第一层；掌握后可设计可维护的指令，并知道不能把可靠性完全押在它上面。

- System Prompt 的作用是让 Agent 以特定形式完成任务，内部可包含角色、工具、规则、格式规范。
- 长上下文下模型可能无视或不遵守 System Prompt；原文举例 Qwen3-8B Flash、DeepSeek V3 等较弱模型，加入 200-400 行 Prompt 后指令遵守能力明显下降。
- 原文认为不能简单归因于“模型不老实”，而是推理生成下一个 token 时注意力没有强到关注 Prompt 所有细节；弱模型普遍使用稀疏化推理和优化手段，会进一步削减注意力功能。
- 在 Claude Opus 4.5 或 GPT-5 上实验出的好 Prompt，迁移到较弱模型上仍可能表现难以接受。
- 首尾两端注意力更强不代表放在首尾的信息一定被关注；注意力机制和 Transformer 在 Agent 开发中基本是黑箱，没有热力图可看模型到底关注什么，因此 System Prompt 的问题是“无解问题”。

**Qwen3-8B Flash、DeepSeek V3、Claude Opus 4.5、GPT-5 快速上手讲解**
- 一句话本质：它们是文中用于对比不同能力档位和部署条件的模型/产品版本。
- 结构化拆解：弱模型在长上下文和指令遵守上更易下降；强模型上有效的 Prompt 不保证迁移；不同版本的服务部署方式会影响实际表现。
- 作用定位：用于说明 Prompt 与 Agent 效果依赖具体模型；选型和测试必须按目标模型做。

对应链条第 2 环：上下文压缩与缓存成本。

**上下文压缩系统快速上手讲解**
- 一句话本质：上下文压缩系统是在上下文变长时删减、摘要或索引化历史内容，以控制输入长度和成本。
- 结构化拆解：输入是历史对话和工具结果；处理方式有摘要、索引替换、截断；输出是更短上下文；需决定何时压缩以及压缩后是否重建缓存。
- 作用定位：解决上下文膨胀；掌握后可设计压缩策略并在效果与缓存成本间权衡。

**LM（语言模型）快速上手讲解**
- 一句话本质：LM 是学习语言规律并生成文本的模型。
- 结构化拆解：输入文本，输出文本；可执行摘要；效果依赖自身注意力和给它的 System Prompt。
- 作用定位：摘要压缩中作为第二个模型压缩当前上下文。

**摘要压缩、索引压缩、截断压缩快速上手讲解**
- 一句话本质：它们是三种把长上下文变短的常用操作。
- 结构化拆解：摘要压缩用另一个 LM 重写上下文；索引压缩把待压缩段落替换为 ID，并把原段落存入临时数据库；截断压缩直接丢弃内容。
- 作用定位：构成上下文压缩的基本组合；原文认为行业套路基本是这几种的排列组合，没有明显更优变种。

- 摘要压缩依赖第二个 LM 的注意力和 System Prompt，长度与精度难以特别好控制；缓解方法是切分后逐段压缩，再重组。
- 索引压缩适合工具返回结果这类外来文本；可与摘要压缩配合，递归寻找过去被压缩时实际替代的内容。
- 截断压缩最简单、最早出现，现在基本没用。
- 压缩难点 1 是确定何时压缩：绝对长度、用户强制要求、相似内容相似度识别。若两个句子相关性很低，可去掉其中一个；典型场景是执行任务时用户插入完全不相关问题，该问题及其回复可去掉。
- 压缩难点 2 是与 KV Cache 重建花费平衡：每次压缩会清除显存中的 KV Cache，之后需重新 Prefill；使用 DeepSeek 这类对缓存命中友好的模型时，频繁压缩会亏很多 token。
- 缓解方法：超过 70% 才压缩；压缩后保证压到 50% 或 40% 以下；设置至少 N 个 token 不允许压缩；预估 token reduction 不能小于 20%，否则不压缩。
- 特殊思路：不考虑 Session 暴露，例如车载语音助手或专门跟老人聊天的对话机器人，可在后台偷偷切换 Session。

**KV Cache、Prefill、Decode 快速上手讲解**
- 一句话本质：KV Cache 是模型推理时缓存已计算的键值表示以加速后续生成；Prefill 是并行处理输入段，Decode 是逐词串行生成。
- 结构化拆解：Prefill 计算输入缓存；Decode 复用缓存逐个生成 token；修改前文会使缓存失效；缓存命中可节约成本。
- 作用定位：解释上下文压缩成本、缓存设计和模型服务指标的基础。

**Session（会话）快速上手讲解**
- 一句话本质：Session 是一次连续交互的会话边界。
- 结构化拆解：包含一组消息和状态；可切换；影响缓存复用和记忆来源；某些产品可不把 Session 暴露给用户。
- 作用定位：上下文压缩、记忆评测和缓存复用的基本单位。

对应链条第 3 环：长期记忆系统。

**Memory 系统与长期记忆快速上手讲解**
- 一句话本质：长期记忆系统是把跨会话需要保留的信息持久化并可按需检索的系统。
- 结构化拆解：包括存储、增删改查、遗忘或二次处理、检索、评测、隔离等部分；短期任务状态通常由上下文自己处理。
- 作用定位：本文记忆部分核心；掌握后可设计可维护记忆并避免串扰。

**CRUD 快速上手讲解**
- 一句话本质：CRUD 是创建、读取、更新、删除四类基础数据操作。
- 结构化拆解：创建写新记录；读取查询；更新修改；删除移除。
- 作用定位：记忆系统最低功能要求之一。

**Milvus、PostgreSQL、Redis 快速上手讲解**
- 一句话本质：Milvus 是向量数据库，PostgreSQL 是关系型数据库，Redis 是内存键值缓存。
- 结构化拆解：Milvus 适合相似检索；PostgreSQL 适合持久化真值；Redis 适合缓存热数据；三者可在记忆、存档、冷热分离中配合。
- 作用定位：文中记忆系统和 Checkpoint 冷热分离涉及的主要存储组件。

- 长期记忆第一点是支持增删改查；可用单纯 CRUD、小型数据库如 Milvus 或 PostgreSQL，也可做大规模团队共享记忆系统，取决于架构。
- 第二点是记忆二次处理：一般做基础遗忘机制，否则记忆越来越多，新记忆检索时优先级不好；部分系统在后台加二次压缩，但有时有用有时不管用。
- 评测系统难做：记忆来源跨不同 Session，可能由不同任务场景、不同模型版本组成，甚至一个 Session 有多个模型参与，很难评价模型在记忆系统中的具体表现。
- 很多论文拿记忆系统刷 benchmark，LoCoMo 和 LongMemEval 已被刷烂；测试集效果好不代表用户侧好用。

**Benchmark、LoCoMo、LongMemEval 快速上手讲解**
- 一句话本质：Benchmark 是标准化评测集；LoCoMo 和 LongMemEval 是文中提到的记忆评测集。
- 结构化拆解：用固定任务和指标比较系统；可被针对性刷分；跨 Session、多模型使真实评价复杂。
- 作用定位：说明记忆系统不能只看榜单效果。

**RAG 快速上手讲解**
- 一句话本质：RAG 是先从外部知识库检索内容再交给模型生成的方案。
- 结构化拆解：包括索引、检索、拼接上下文、生成；可用于记忆检索；但可能使系统过重。
- 作用定位：记忆系统可选方案，但原文认为一般不必太重，可能只需简单 Markdown。

- 值得关注点 1 是 memory 延迟：查一次记忆若需几秒，大部分 Agent 系统不可接受。
- 点 2 是召回准确率：可用合成数据集测试，把数据塞进记忆后再检索能否匹配；与 RAG 操作相似，但记忆系统加 RAG 可能太重。
- 点 3 是时间有效性：可在增删改查上加时间过滤系统。
- 点 4 是用户间记忆干扰：保证各用户记忆独立；多个子 Agent 的记忆有时可共享、有时不该共享，需要单独设计。
- 点 5 是工具记忆串扰：不同意图场景下对工具调用的印象会互相干扰。例子：coding 场景下 Agent 可能形成“Git 对 coding 没什么用”的记忆，但查文档场景 Git 又很好用；不处理会导致未来无视某个工具。
- 点 6 是无证据记忆：Agent 对某事务留下印象，但该印象不一定有证据或只在特殊场景成立；应保证证据和记忆一对一匹配，避免未来错误干扰任务。数据化记忆可再用 LLM 看一遍记忆如何压缩。

**工具记忆串扰、无证据记忆快速上手讲解**
- 一句话本质：工具记忆串扰是不同意图下对工具的印象互相污染；无证据记忆是记忆缺少可匹配证据。
- 结构化拆解：按意图隔离工具记忆；为记忆绑定证据；必要时用 LLM 二次检查记忆。
- 作用定位：提升记忆可靠性，避免错误记忆干扰后续任务。

对应链条第 4 环：通用/特化 Agent 与框架选择。

**通用 Agent、特化 Agent 快速上手讲解**
- 一句话本质：通用 Agent 面向广泛任务，特化 Agent 面向特定业务场景。
- 结构化拆解：通用方案依赖大模型和通用工具，调用多、成本高；特化方案可解耦 Prompt、Skill、工具，并用便宜模型分担任务；业务上框架可替换，成本上特化可更低。
- 作用定位：面试解释为何不直接用 Codex 等通用方案。

**LangGraph 快速上手讲解**
- 一句话本质：LangGraph 是用于构建 Agent 工作流的框架/容器。
- 结构化拆解：组织节点和状态；默认支持 Redis 和 PostgreSQL 存档；生态有追踪分析工具；企业常把 Prompt、Skill、工具外置解耦。
- 作用定位：简历关键词和工程组织；但原文强调 LangGraph 本身不重要，重要的是外围系统与生态。

**Prompt/Skill 中心管理系统、Skill 快速上手讲解**
- 一句话本质：Prompt/Skill 中心是集中管理提示词和可复用任务能力的内部系统；Skill 是可复用的任务能力或操作说明集合。
- 结构化拆解：存储 Prompt、Skill、可能工具配置；与工作流代码解耦；便于复用和治理；Skill 与 MCP 没有直接关系。
- 作用定位：解释业务上 LangGraph、Codex、Workflow、Buddy 等可替换。

**Codex 快速上手讲解**
- 一句话本质：Codex 是文中指代的通用编码/任务 Agent 产品。
- 结构化拆解：执行任务会多次调用外部 API；消耗 token 和 TPM；成本较高。
- 作用定位：作为通用方案与自建特化 Agent 对比。

**Workflow、Buddy 快速上手讲解**
- 一句话本质：原文仅提及它们是可替代 LangGraph 的方案名称。
- 结构化拆解：原文未展开其组成和机制，笔记不补充编造。
- 作用定位：用于说明业务上框架可替换。

- 业务解释：LangGraph 本身不重要，重要的是额外系统；有规模企业一般有单独 Prompt 和 Skill 中心管理系统，LangGraph repo 里可能没有 Prompt、Skill、tool，只是简单容器，其他东西解耦；此时用 LangGraph、Codex、Workflow、Buddy 都无所谓，用官方还更灵活。
- 成本解释：同一个 Agent 在 token 上很不经济；Codex 执行简单任务可能调用 20-30 个外部 API，API 调用有花费，后台运行 Agent 也消耗大量 token；用 Codex 还要考虑 TPM。自建可用便宜模型做不需要强推理的任务，成本可能降到十分之一、二十分之一。

**TPM 快速上手讲解**
- 一句话本质：TPM 是每分钟 token 数配额或指标。
- 结构化拆解：限制模型调用吞吐；影响并发和成本；企业高并发需购买企业服务。
- 作用定位：通用 Agent 成本与容量考量。

**Dify、LangChain、AutoGen、MetaGPT、CrewAI、OpenAI、Google ADK 快速上手讲解**
- 一句话本质：这些是构建 Agent 工作流、多 Agent 协作或相关生态的框架/产品。
- 结构化拆解：Dify 是 LangChain 延伸的多 Agent 框架，原文认为太重；MetaGPT 和 CrewAI 偏角色扮演多 Agent，只在多 Agent 场景有用；OpenAI 和 Google ADK 有生态绑定问题。
- 作用定位：框架选择需看重量、场景匹配和锁定风险。

**LangSmith、Langfuse、Spring Boot 快速上手讲解**
- 一句话本质：LangSmith 和 Langfuse 是 trace 分析工具；Spring Boot 是后端开发框架。
- 结构化拆解：LangSmith 有会员和按条收费机制；Langfuse 是常用追踪工具；Spring Boot 用于说明 Agent 框架很难做成通用后端框架式标准。
- 作用定位：LangSmith 是使用 LangGraph 的主要理由之一；Spring Boot 用于对比说明 Agent 应用与 LLM API 耦合深、难完全解耦。

- 简历框架选择：有人建议纯手写，但关键词匹配可能有问题；最好加 LangGraph，匹配度比 AutoGen 和 OpenAI 的几个框架高很多。
- 面试问为何用 LangGraph 的标准答案：LangGraph 不重要，重要的是生态；常用 trace 分析工具有 LangSmith、Langfuse；LangGraph 公司盈利模式是收 LangSmith 订阅费，超出会员限额按条数收费。
- 自己从头搭也会遇到工具策略、工具调用、重试流程等问题，最后仍是重工程，用 LangSmith 差不多。
- Agent 框架很难做成 Spring Boot 式效果，因为 Agent 应用与 LLM API 高度耦合，很多工程细节难解耦。

对应链条第 5 环：缓存分层与模型选型。

**Prompt Cache、Application Cache、Hash Table 快速上手讲解**
- 一句话本质：Prompt Cache 是在多个 Session 间共享已计算的 KV Cache block；Application Cache 是应用层对完整输入做哈希命中并直接返回结果的缓存；Hash Table 是按键快速存取值的数据结构。
- 结构化拆解：Prompt Cache 复用相同前缀的缓存块；Application Cache 用哈希表匹配输入与输出，命中则跳过推理；KV Cache 和 Prompt Cache 属推理层，Application Cache 属应用层。
- 作用定位：降低重复前缀成本、服务评测 pipeline；但 Application Cache 在一般 Agent 中命中率低。

**Semantic Cache 快速上手讲解**
- 一句话本质：Semantic Cache 是按语义相似度匹配历史请求并复用结果的缓存。
- 结构化拆解：基于相似度匹配 Application Cache；可扩大命中率；会牺牲可靠性，可能误驱逐用户请求。
- 作用定位：Application Cache 的变种，用于节省资源但需接受误命中风险。

**Bloom Filter、Cuckoo Filter 快速上手讲解**
- 一句话本质：它们是判断元素是否可能存在的概率数据结构。
- 结构化拆解：Bloom Filter 用位数组和多个哈希；Cuckoo Filter 支持删除并有更高空间效率；都存在假阳性。
- 作用定位：传统后端常用于避免无效数据库查询；但 Application Cache 命中率低时作用有限。

- Prompt Cache 与 KV Cache 不是对立关系，都是特定引擎该干的事；引擎里两者共享同一套 KV Cache block。KV Cache 指单个 Session 上下文往后推进，Prompt Cache 指多个 Session 共享 KV Cache block，可同时发生。
- 例子：“你是一名专业助手，我问什么是 Attention，我问什么是 Transformer”，开头部分可共享，即 Prompt Cache，提高预填效率。
- Application Cache 是应用层缓存，基本是 Hash Table，对输入 prompt 做命中，命中直接返回结果并跳过推理；一般 Agent 命中率非常低，比如豆包很难有两个用户问一字不差的问题。
- Application Cache 常用于评测 pipeline，因为内容已存在缓存中，读取方便；Semantic Cache 用相似度扩大命中，但牺牲可靠性。
- Application Cache 若当应用需数据库，数据库不存在时消耗大；可用 Bloom Filter 或 Cuckoo Filter 做前置存在性判断，但 Application Cache 命中率低，这两个东西在这里也没太大用。
- 缓存友好压缩想法：传统 Attention 机制不破坏 KV Cache；现有压缩把 A 段压缩成 S，B 段依赖 A，A 和 B 的 KV Cache 都不要。若把压缩后的 S 放到 B 之后，做成 ABS 形式，则流程不破坏 B 的 KV Cache；但会破坏语义因果性，把结果塞到原因后面。原文称这是未被确认的想法，不知道为什么大家没用。

**Dense 模型、MoE 模型快速上手讲解**
- 一句话本质：Dense 模型推理时激活全部参数；MoE 模型只激活部分专家参数。
- 结构化拆解：Dense 参数量等于推理激活量；MoE 总参数大但激活少；专家能力分配不透明；不能按参数量比例判断表现。
- 作用定位：模型选型需看实际能力而非总参数量。

**FP8、FP4、FP2 快速上手讲解**
- 一句话本质：它们是模型权重或计算的低精度格式。
- 结构化拆解：FP8 较常用；FP4 量化损失可接受但不一定最好；FP2 很激进，压缩后劣化严重；推理引擎优化会影响表现。
- 作用定位：本地部署和模型服务选型需考虑量化损失。

**TTFT、TPS、TPM、RPM、并发请求数快速上手讲解**
- 一句话本质：它们是模型 API 的体验、吞吐和配额指标。
- 结构化拆解：TTFT 是请求到首 token 时间；TPS 是每秒 token 数；TPM 是每分钟 token 数；RPM 是每分钟请求数；并发请求数控制同时调用量。
- 作用定位：C 端体验和企业容量规划的关键指标。

- Dense 模型几乎全量参数激活，如 32B 就真的全部激活，参数量等于推理激活量；MoE 只激活可能十分之一参数，总参数显得虚，参数量不再代表实际能力。
- 无法对 MoE 与 Dense 表现做比例判断，因为不知道 MoE 各专家能力如何分配；原文体感 235B MoE 可能激活约 30B，但表现不会像 30B Dense，可能稍强，仅限其使用场景。
- 本地部署 120B 模型到单卡，多数用 MoE 配合 FP8、FP4 优化；FP4 测得多、量化不特别严重；FP2 激进，绝大部分情况下劣化非常严重；OpenRouter 自部署 DeepSeek 时可在推理引擎做手脚，表现可能变差。
- TTFT 影响用户体验；Decode 速度影响 token 生成速度；公司内部或后台 Agent 有时不必过度考虑速度，C 端 Agent 的 Prefill、Decode 速度都会明显影响体验。
- KV Cache 有命中后节约成本机制，不要莫名修改前文上下文；以前有设计往 System Prompt 塞时间戳，会彻底破坏 KV Cache，不建议。
- TPS、TPM 控制 Decode 速度；RPM 和并发请求数控制同时调用量；DeepSeek 不会给普通用户无限并发，企业几千几万并发需买企业服务。

对应链条第 6 环：工具调用与可靠性治理。

**Function Call 快速上手讲解**
- 一句话本质：Function Call 是模型在生成时输出结构化工具调用请求的能力。
- 结构化拆解：模型识别需要调用工具；输出 tool_calls 字段；Harness 框架检测并执行；可靠性受模型和推理引擎影响，需要兜底。
- 作用定位：模型与 Agent 工具之间的接口。

**MCP、SSE、MCP server、MCP client 快速上手讲解**
- 一句话本质：MCP 是工具提供方与 Agent 工具之间沟通的通用规范；SSE 是服务器向客户端持续推送事件文本的协议。
- 结构化拆解：MCP server 运行在工具提供方，MCP client 运行在 Agent 侧；通过 MCP 配置 JSON 接入 Codex 或 Cursor 的 Settings；常用 SSE 类协议沟通。
- 作用定位：工具接入标准化；MCP 与 Function Call 不是同一层关系，MCP 与 Skill 也没有直接关系。

**Cursor 快速上手讲解**
- 一句话本质：Cursor 是文中提到的可放置 MCP 配置的编辑器/开发工具。
- 结构化拆解：原文仅说明可把 MCP 配置 JSON 放到其 Settings 中；未展开更多机制。
- 作用定位：MCP 接入的示例产品。

- Function Call 和 MCP 常被一起问，但从技术结构看关系不大：Function Call 更接近 LLM 与 Agent/Harness 工具沟通的阶段；MCP 更接近工具提供方与 Agent 工具沟通的阶段。
- Function Call 由模型方在预训练或后训练阶段训练；模型识别需调用工具时输出 tool_calls 字段，Harness 检测后调用对应工具；可在 Prompt 中额外强调更稳妥。
- Function Call 实际出错概率挺大；结构化输出承诺正确 JSON 格式很多时候是忽悠；团队测试发现 Function Call 仍受推理引擎干预，推理引擎持续优化会有 bug，不能把 Agent 可靠性全靠在别人推理引擎上，需要兜底。
- MCP 不用也可以；有人把 Skill 和 MCP 放一块，原文强调二者一点关系都没有。

**JSON Schema 快速上手讲解**
- 一句话本质：JSON Schema 是描述 JSON 数据字段、类型和约束的规范。
- 结构化拆解：定义字段名、类型、必填、枚举等；用于校验工具参数；减少格式错误。
- 作用定位：工具调用第一道技术校验。

**Token Bucket、滑动窗口快速上手讲解**
- 一句话本质：它们是控制请求速率的限流算法。
- 结构化拆解：滑动窗口统计时间窗口内请求数；Token Bucket 以固定速率补充令牌并放行请求，桶满限制突发。
- 作用定位：Agent 对工具调用限流，避免压垮工具。

**幂等性快速上手讲解**
- 一句话本质：幂等性保证同一请求最多执行一次，或多次执行结果一致。
- 结构化拆解：为请求分配幂等 ID；服务端记录已处理 ID；重复请求返回原结果；工具侧也需负责。
- 作用定位：防止重试导致重复转账等副作用。

- 工具 schema 要做技术校验：JSON 格式、字段、参数等。
- 调用超时要重试；模型可能重复调用工具 3-5 次，一般设重试上限；每次重试希望返回错误信息字段；服务挂了要告诉模型工具确实挂了，否则模型不停试且不知道已调用过，浪费 token。
- 要考虑工具调用量压力，对每个 Agent 限流；方案有滑动窗口或 Token Bucket；原文认为滑动窗口仍主流，并未被彻底淘汰。
- 调用工具时间可做随机抖动，如第 5 秒调成 5.2 或 5.8 秒；但原文感觉大规模数据来时抖动不能彻底错开，意义不大。
- 等待时间可指数上升：第一次失败等 1 秒，第二次 2 秒，第三次 4 秒，第四次 8 秒；部分 Agent 在等待时同时调其他工具，也有并发调用设计。
- 幂等性与传统后端一致：防止用户转账 100 元因网络卡同时发两个请求变成转 200 元；每个请求加幂等 ID，保证最多执行一次；Agent 要为每个工具设幂等机制，工具侧也要负负载均衡、分布式部署、拆分等责任。

对应链条第 7 环：Checkpoint 与 Router。

**Checkpoint 快速上手讲解**
- 一句话本质：Checkpoint 是 Agent 上下文的持久化存档。
- 结构化拆解：保存为 JSON 或存入 Redis/PostgreSQL；每次对话加载；大量加载会 IO 放大；需分库分表和冷热分离。
- 作用定位：恢复会话和状态管理。

**冷热分离、旁路缓存快速上手讲解**
- 一句话本质：冷热分离把热数据放缓存、冷数据和真值放数据库；旁路缓存读先查缓存再查库，写先写库再删缓存。
- 结构化拆解：Redis 放热缓存，PostgreSQL 放正式版本；读优先 Redis，未命中再读 PostgreSQL；写先写 PostgreSQL，同时删除 Redis 旧缓存；会有短暂不一致窗口。
- 作用定位：降低 Checkpoint 加载 IO，Agent 场景并发同 Session 写少，因此该策略基本够用。

**Upstash 快速上手讲解**
- 一句话本质：Upstash 是提供托管持久化数据服务的产品。
- 结构化拆解：免自建冷热分离流程；提供产品化持久化保存服务。
- 作用定位：不想自己写存档流程时的可选服务。

- LangGraph 默认已支持 Redis 和 PostgreSQL，不需要很多外设即可支持冷热分离。
- Checkpoint 每次发消息都重新加载，全部打数据库且 Agent 多时 IO 可能被打爆，数据大时读放大严重；需分库分表，条件允许可多部署 PostgreSQL、Redis，按用户切割。
- 简单冷热分离：Redis 缓存，PostgreSQL 正式版本；开始时旁路缓存读取，优先 Redis，未命中读 PostgreSQL；写先写 PostgreSQL，同时删除 Redis 旧缓存。
- 该策略有短暂窗口：两个服务并发使用同一 Session，写和读同时发生会导致 Redis 与 PostgreSQL 不一致；但 Agent 场景很难想象两个服务同时写一个 Session 且值不同，基本够用。
- 不想自己写可走 Upstash 这类特化数据服务商。

**LLM API Router、Gateway、意图识别、模型分发快速上手讲解**
- 一句话本质：LLM API Router 是 LLM 调用路由层，做意图识别和模型分发；Gateway 更多由传统后端中间件团队处理。
- 结构化拆解：Router 判断任务类型并分发到对应模型；简单规则可按 coding、图像等匹配；复杂方式用便宜小模型输出 dict array，包含意图、置信度、能力需求；Harness 获取 JSON 后匹配后端维护的模型系统。
- 作用定位：Agent 工程化路由，平衡成本、延迟和缓存损失。

- Router 类似网关，但 Gateway 和 Router 现在分得比较清楚；Router 一般做意图识别和模型分发。
- 简单规则：coding 任务分到 coding 模型，图像任务分到图像模型。
- 复杂规则：用 1B 或 10B 级便宜模型，token 消耗可无视，推理快；System Prompt 长期加载在 KV Cache 中命中率高；输出 dict array，例如意图 coding、置信度 0.9、是否需要推理能力、是否需要图像能力等；Harness 拿 JSON 匹配模型。
- 意图识别用户广、延迟要求高，条件允许可把流程刻在硬件里固定运行，提高推理速度。
- 规则和意图可一起用；注意切换模型会放弃模型上的 KV Cache，要做成本考量，例如只允许模型单向升级，避免从大模型切到小模型丢掉已积累缓存。
