# 学习笔记：视频内容整理

## 精华版

视频的主线是：模型可以提出候选的下一步，但候选不等于已验证的事实；业务任务中必须由程序用明确的领域概念定义去核对对象、关系、状态和参数。领域概念定义需要共享且形式化，让程序能依据声明推出新结论或发现不一致。核对要接入智能体运行循环：模型提出工具调用建议，应用程序实际执行；检查尽量放在有外部副作用的动作提交之前，失败时回传具体原因，并明确是否重试、重试几次、何时停止或交给人处理。入口参数检查与业务状态检查职责不同：前者检查输入结构与类型，后者检查业务含义与关系。检查若只记录日志却不影响执行，就没有发挥作用。看一个智能体方案，应沿运行路径追问三件事：模型交出了什么、检查用了哪些事实和声明、检查结果能否真正影响动作。

## 整体逻辑链条梳理

1. **对应链条第 1 环：先区分“模型提出的候选”与“已有依据的事实”。**  
   模型输出只是待验证候选，业务任务不能把模型的肯定当作事实。为什么成立：视频明确区分探索、想象与业务事实。衔接下一环：核对候选需要明确的领域含义。

2. **对应链条第 2 环：用本体表达领域知识，再用知识图谱承载对象与关系。**  
   本体提供共享、形式化的概念说明；知识图谱把相关对象和关系直接呈现。为什么成立：程序要依据明确结构和语义工作，图是否漂亮不能替代含义声明。衔接下一环：本体需要来源和建模方法。

   **术语首现讲解：本体（Ontology）**  
   - 一句话本质：本体是对一个领域中共用概念及其关系、属性、规则的形式化说明。  
   - 结构化拆解：  
     - 组成：概念或类别、具体对象、属性、关系、规则；  
     - 解决什么问题：让“订单、买家、负责人”等词在系统中尽可能指向同一套含义；  
     - 关键机制：用明确结构和语义写出概念与关系，使程序可以依据定义推导和核对。  
   - 作用定位：本文中它是核对模型候选结果的领域知识底座；掌握后可用于定义业务对象、关系和规则，支撑后续推理与校验。

   **术语首现讲解：知识图谱**  
   - 一句话本质：知识图谱是用节点、边和属性组织对象与关系的图结构知识表示。  
   - 结构化拆解：  
     - 组成：节点表示类别或具体对象，边表示关系，属性描述特征；  
     - 解决什么问题：让相关对象和关系较容易被直接看见、查询和组合；  
     - 关键机制：要能说清节点表示类别还是具体对象、一条线从谁指向谁、线上关系允许什么判断。  
   - 作用定位：本文中它可作为知识表示载体，但图本身不能替代本体声明。

   **术语首现讲解：神经符号 AI（Neuro-Symbolic AI）**  
   - 一句话本质：神经符号 AI 是把神经网络的开放表达处理与符号知识的明确声明、推导结合起来的方法方向。  
   - 结构化拆解：  
     - 组成：一边是模型根据上下文提出候选，一边是名称、类别、关系和逻辑表达等符号知识；  
     - 解决什么问题：既保留模型处理开放式表达的能力，又让系统能依据已声明含义核对；  
     - 关键机制：模型提出候选，符号知识参与推导和检查，二者在同一任务里配合。  
   - 作用定位：本文的总框架；掌握它有助于理解为什么大模型和本体不是互相替代关系。

3. **对应链条第 3 环：本体来源可自上而下，也可自下而上，并可复用常见词汇。**  
   自上而下由领域专家定义对象、属性、关系和规则；自下而上从资料、反馈和记录中发现反复出现的对象与关系。为什么成立：既要确认领域含义，也要从实际数据中发现建模线索。衔接下一环：有了声明后，系统才能推理。

   **术语首现讲解：专家系统 / 基于规则的系统**  
   - 一句话本质：专家系统或基于规则的系统是把领域规则显式写入程序以做判断的系统。  
   - 结构化拆解：  
     - 组成：规则库、执行或推理机制；  
     - 解决什么问题：在特定领域按显式规则判断；  
     - 关键机制：匹配条件后执行结论；视频回顾上世纪 80 年代专家系统投入高但难扩展。  
   - 作用定位：本文中作为符号知识路线的历史参照，说明今天要把符号知识和大模型接起来。

   **术语首现讲解：Schema.org、FOAF、Dublin Core、DBpedia、Wikipedia**  
   - 一句话本质：它们是可复用的常见词汇表或结构化知识来源。  
   - 结构化拆解：  
     - Schema.org 提供常见对象和属性词汇；  
     - FOAF 可描述人和社交关系；  
     - Dublin Core 常用于描述文献资源及元数据；  
     - DBpedia 从 Wikipedia 提取结构化信息，让知识可被查询和复用；Wikipedia 是开放协作编辑的在线百科全书，本文只把它作为 DBpedia 的数据来源；  
     - 解决什么问题：减少从零发明词汇；关键机制：复用词汇，但核对原始定义和领域使用范围。  
   - 作用定位：本文中作为本体建模的复用起点。

4. **对应链条第 4 环：用 RDFS 和 OWL 依据声明推导或发现不一致。**  
   RDFS 提供基础类别和属性语义；OWL 可写更丰富的本体公理。为什么成立：推理不是模型凭感觉，而是根据定义推导；结论依赖前提，前提错则结论错。衔接下一环：推理结论还要由业务程序决定通过、修正、停止还是交给人。

   **术语首现讲解：RDFS、OWL 及其关键声明**  
   - 一句话本质：RDFS 提供基础类别和属性语义，OWL 可写具有明确逻辑含义的丰富本体公理。  
   - 结构化拆解：  
     - Domain 与 Range：Domain 可理解为关系左侧对象所属类别，Range 是右侧对象所属类别；它们可推出关系两端对象的类型，但不天然等于“预检不对就拒绝保存”的类型校验。  
     - 推理（Inference）：根据已有事实和明确声明推出新结论；输入是事实与声明，输出结论依赖前提。  
     - 传递属性：若 Ancestor 被声明为传递属性，Sue 是 Mary 的祖先、Mary 是 Anna 的祖先，可推出 Sue 也是 Anna 的祖先。  
     - 功能性属性（Functional Property）：对同一主体经由该属性至多关联一个对象；可推出两个名称指同一对象，若再声明二者不同则出现不一致。  
     - 类互斥：声明同一个对象不能同时属于两个类；视频示例把 Customer 与 Support Rep 声明为互斥类。  
     - 推理器：执行 RDFS/OWL 声明推导的软件组件；推理器得到结论与业务程序拒绝一次操作是两个需要衔接的动作。  
   - 作用定位：本文中是核对候选结果的推理层；掌握后能判断哪些结论由声明推出，哪些仍需程序校验和业务处理。

5. **对应链条第 5 环：Agent 是反复观察、决定、行动的循环，必须明确停止条件。**  
   循环让一次处理能反复进行，也带来结果一直不对仍重试、多 Agent 消息越跑越偏、时间和 token 持续消耗等问题。为什么成立：持续尝试必须有停止与失败去向。衔接下一环：工具调用循环展示检查应插入哪里。

   **术语首现讲解：Agent（智能体）**  
   - 一句话本质：Agent 是一个反复感知环境、做出决定并采取行动的程序过程。  
   - 结构化拆解：  
     - 组成：感知或输入、决策或规划、行动或工具调用；  
     - 解决什么问题：让程序持续做事并依据新结果调整下一步；  
     - 关键机制：看当前信息、决定下一步、调用能力拿结果、再决定是否继续；循环必须明确何时停止。  
   - 作用定位：本文中它是把模型候选动作接入程序执行和检查的主线。

   **术语首现讲解：大语言模型（LLM）**  
   - 一句话本质：大语言模型是根据上下文生成后续内容的模型。  
   - 结构化拆解：  
     - 组成：模型参数与上下文输入；  
     - 解决什么问题：处理开放式表达，提出候选判断或下一步；  
     - 关键机制：根据任务、对话记录和工具说明生成自然语言或结构化调用建议；不负责实际执行和最终业务校验。  
   - 作用定位：本文中它承担 Agent 的部分判断和规划，但候选结果仍需程序核对。

6. **对应链条第 6 环：工具调用循环中，模型提出建议，应用执行并检查。**  
   应用把任务、对话记录和工具说明交给模型；模型返回工具调用块和 Stop Reason；当 Stop Reason 为 tool_use 时程序进入工具分支。为什么成立：返回调用建议不等于动作已经发生，应用可在有副作用动作前安排检查。衔接下一环：检查需要入口校验和领域校验分工。

   **术语首现讲解：Claude 客户端工具调用循环、Stop Reason、工具调用块、副作用**  
   - 一句话本质：Claude 客户端工具调用循环是模型提出工具调用建议、应用程序实际执行工具并把结果回传模型的循环。  
   - 结构化拆解：  
     - 工具调用块：返回内容中包含工具名称和参数的结构化块；  
     - Stop Reason：本次响应为什么停下来；为 tool_use 时表示当前响应要求使用工具；  
     - 副作用：一次运行是否真正改变外部状态；只读数据、计算结果、准备候选结果通常未改变外部状态，修改数据库、发出付款会改变外部状态；  
     - 关键机制：应用提取调用内容和参数，执行允许执行的工具；检查尽量安排在提交前；结果要转成检查程序能理解的对象、关系、状态，再与事实和声明核对；失败原因具体回传。  
   - 作用定位：本文中它展示检查应插入运行循环的位置；掌握后能判断检查是在提交前还是事后补救。

7. **对应链条第 7 环：Pydantic 做入口检查，本体做业务状态检查。**  
   入口核对参数、结构和类型；准备把结果纳入业务状态时，再核对领域含义和关系。为什么成立：两类检查职责不同，工具能力可以重叠。衔接下一环：用错误示例检验这些检查是否真正参与程序判断。

   **术语首现讲解：Pydantic、Python、类型转换、自定义断言、模型校验**  
   - 一句话本质：Pydantic 是一种根据数据模型检查输入的数据验证工具。  
   - 结构化拆解：  
     - Python 是动态类型编程语言，变量可先指向整数再指向文字，因此对象仍需明确本次输入要求；  
     - 组成：字段类型、数据结构要求、是否允许类型转换的配置；  
     - 关键机制：支持自定义断言和模型校验，有条件和无条件的检查都可写入；断言是自定义检查条件，模型校验是对整个模型对象做检查；  
     - 解决什么问题：在入口核对参数和结构。  
   - 作用定位：本文中负责“入口检查”；掌握后能与本体“业务状态检查”分工。Coyle 的话可理解为：Pydantic checks at the door, and ontology checks at the ledger。

8. **对应链条第 8 环：错误示例分别检验对象同一性、关系和状态取值。**  
   同一订单又出现退款，要核对对象是否同一个并让检查结果控制提交；把钱付给客服而非订单买家，要核对付款对象与订单买家关系；模型给出 Probably Shipped，程序需要明确允许状态并让校验器检查。为什么成立：业务要求必须表达清楚并参与程序判断。衔接下一环：形成可追问的 Agent 方案检查路径。

9. **对应链条第 9 环：沿运行路径追问 Agent 方案是否闭环。**  
   先看模型交出了什么，再看检查用了哪些事实和声明，最后看检查结果能否真正影响动作。为什么成立：只画一个叫本体的框，若输入、输出和失败分支未说清，方案仍有工作要做。衔接收尾：结论落回主线，并列出开放问题。

## 一句话结论

对应链条第 9 环（结论收束）：模型能提出候选下一步，但只有把领域含义形式化、用推理与校验核对，并让检查结果控制执行与停止，Agent 循环才可靠。

## 核心要点

1. 对应链条第 2 环：本体是对共享概念体系的形式化说明，核心是对象、属性、关系和规则，不是图是否漂亮。  
2. 对应链条第 3 环：本体来源可自上而下由专家定义、自下而上从资料抽取，并可复用常见词汇但需核对领域定义。  
3. 对应链条第 4 环：RDFS/OWL 能依据声明推出类型、间接关系和同一性并发现不一致，但结论依赖前提且推理结论不等于业务拒绝。  
4. 对应链条第 5 环：Agent 是感知—决定—行动的循环，接入模型后必须明确停止条件、重试次数和失败去向。  
5. 对应链条第 6 环：工具调用循环中模型只提出调用建议、应用负责执行，检查应尽量放在有副作用动作提交前并把具体失败原因回传。  
6. 对应链条第 7—8 环：Pydantic 负责入口参数与结构检查，本体负责业务状态与关系检查，检查结果必须能影响执行而不是只记日志。

## 关键细节

对应链条第 2—8 环。

- Bob teaches Scooter；Teaches 的 Domain 是 Teacher、Range 是 Student，可推出 Bob 是 Teacher、Scooter 是 Student；若声明所有 Teacher 都属于 Person，可推出 Bob 也是 Person。  
- Sue 是 Mary 的祖先，Mary 是 Anna 的祖先；Ancestor 声明为传递属性，可推出 Sue 是 Anna 的祖先。  
- Jamin 的父亲是 Bob，Jamin 的父亲又写成 Bb；功能性属性可推出 Bob 和 Bb 是同一个人的两个名称；若再声明 Bob 和 Bb 不是同一个人，则出现不一致。  
- Coyle 的话：“Pydantic checks at the door, and ontology checks at the ledger.” 可理解为入口核对参数，准备把结果纳入业务状态时再核对领域含义和关系。  
- 错误示例一：同一订单又出现一笔退款；示例政策设定一张订单只能有一次退款，功能性属性本身不会替支付系统执行拒绝，检查结果还要控制提交并与实际系统约束配合。  
- 错误示例二：把钱付给客服而不是这张订单的买家；示例把 Customer 与 Support Rep 声明为互斥类，若同一账户同时归入两类会产生不一致；实际付款还要核对付款对象和订单买家的关系。  
- 错误示例三：系统直接说 Paid、Shipped、Refunded 等状态，模型给出 Probably Shipped；程序需要明确允许取值，并让实际校验器检查，缺少发货事实不能靠“大概”补成已发货。  
- Schema.org 提供常见对象和属性词汇；FOAF 可描述人和社交关系；Dublin Core 常用于描述文献资源及元数据；DBpedia 从 Wikipedia 提取结构化信息。  
- 上世纪 80 年代专家系统投入高但难扩展；今天谈符号知识是把它和大模型接起来，在具体领域发挥作用。

## 原文没有讲清的问题

对应链条第 9 环的开放问题。

- 具体选用哪类推理器、支持哪些 OWL 子集、推理性能和工程成本如何，视频未展开。  
- 本体声明与现有关系数据库约束、支付系统约束如何分工、同步和冲突处理，视频未展开。  
- 失败回传模型后的重试策略只提“要明确”，未给重试次数、停止阈值、人工介入条件的具体方案。  
- 如何自动从资料中抽取本体、如何评估抽取质量、领域专家如何确认，视频未展开。  
- 多 Agent 互相传消息导致越跑越偏时如何检测和治理，视频未展开。  
- 有副作用工具提交前，检查通过后才提交的实现模式与并发、回滚问题，视频未展开。

## 逐环回收

1. **第 1 环已闭环**：模型输出是候选，不能替代核对；这是后文本体、推理和校验的起点。  
2. **第 2 环已闭环**：本体和知识图谱提供可处理声明与关系表示；开放点是声明质量如何保证。  
3. **第 3 环已闭环**：本体来源有自上而下、自下而上和复用词汇三条路径；开放点是抽取与专家确认流程。  
4. **第 4 环已闭环**：RDFS/OWL 可推出类型、间接关系、同一性并发现不一致；开放点是推理器选型与性能成本。  
5. **第 5 环已闭环**：Agent 循环必须处理停止条件、失败去向和重试；开放点是具体策略参数。  
6. **第 6 环已闭环**：工具调用循环中模型建议、应用执行，检查应前置于副作用并回传失败原因；开放点是有副作用提交的实现模式。  
7. **第 7 环已闭环**：Pydantic 入口检查与本体领域检查分工明确；开放点是与现有数据系统约束的集成。  
8. **第 8 环已闭环**：错误示例分别落到对象同一性、关系和状态取值；共同结论是业务要求要表达清楚并参与程序判断。  
9. **第 9 环已闭环**：看 Agent 方案沿“模型交出什么—检查用了哪些事实和声明—检查结果能否影响动作”追问；尚未闭环的是具体工程实现与治理细节，属于开放问题。

## 原文文案

做 AI 产品、开发 Agent 的，或者负责企业 AI 落地的同学，这期我们把本体和 Agent 的运行循环系统地梳理一遍。借 Frank Coyle 的这场演讲，从 Ontology、知识图谱到 RDFS 和 OWL 推理，再到工具调用和 Pydantic 校验，看看它们到底怎么配合。先看 Agent。在人工智能里，这个概念有很长的历史，远早于今天的大模型。它最基本的动作是感知环境、做出决定、采取行动，你可以把它理解成一个反复观察、判断和行动的过程。现在大家熟悉的很多 Agent 把其中一部分判断和规划交给了大语言模型。Ontology 则来自另一条知识传统，哲学里它讨论什么存在，怎样分类。到了知识工程里，我们关心的范围会具体得多，在这个领域中有哪些东西、它们怎样关联，这些关系究竟是什么意思。我们需要把共同使用的概念明确写出来，让系统能够依据这些定义工作，这里有个常见定义叫对共享概念体系的形式化说明。听起来很绕，我拆开说，共享，意味着大家说订单、买家、负责人的时候尽可能只向同一套含义。形式化，意味着这套含义不能只靠人意会，它要用明确的结构和语义表达，让程序可以处理。现在把两个方向接起来，一边是大模型，根据上下文提出候选处理开放式表达。另一边是形式化的知识，让系统根据已声明的含义推导和核对。这种神经网络与符号知识结合的思路通常叫神经符号 AI，Neuro-Symbolic AI，这里的符号没有那么神秘，名字、类别、关系再加上明确的逻辑表达，都是它处理知识的方式。基于规则的系统属于这个方向，知识图谱也可以承担其中的知识表示，大模型和这套知识不需要互相替代，我们要看它们怎样在同一个任务里配合。但模型能提出多种可能，探索和想象也有价值，但在业务任务里我们得分清，是待验证的想法还是已经有依据的事实。候选结果需要核对，模型说的肯定，也不能代替这一步，先看本体怎样表达知识，比如一个客户下了一张订单，客户和订单是两类对象，下单是它们之间的关系。客户可以有名字和联系方式，订单可以有编号、金额和状态，这些是属性，再加上订单包含的商品，或者订单关联的退款记录，就会形成一张关系图。先别急着把它想成一张非常大的企业知识图谱，看最小的一条关系就够了。你要能说清楚，这个节点表示一类东西还是某一个具体对象，一条线从谁指向谁，线上的动词到底允许我们做什么判断。图谱的漂亮并不能替我们回答这些问题，图的表示方式让相关对象和关系比较容易被直接看见，这里我补充一点，本体的价值还要往前走一步，我们对这些对象和关系做了什么明确声明。关系数据库同样可以表达关系、调整结构，关键仍然是含义有没有定义清楚，以及这些定义有没有进入系统。那本体从哪里来？可以从两个方向入手，自上而下就是找熟悉领域的人把对象、属性、关系和规则处理出来。比如组织里究竟怎样定义客户，哪一种记录算订单，一个状态又是什么意思。这里要把不同人对同一概念的理解问清楚。这条路并不是今天才出现，Coyle 回顾了上世纪 80 年代的专家系统，当时人们基于很高期望也投入了很多资源，但他强调这些系统很难扩展。今天在谈符号知识是把它和大模型接起来，在具体领域里发挥作用。这也呼应了前面说的神经符号思路。另一种是自下而上，从已有资料、客户反馈和实际记录里，找出正在反复出现的对象和关系。发现有一个现有定义装不进去的情况，就回去核对，是数据有问题，还是我们的概念漏掉了什么。抽取出来的内容是建模线索，领域中的定义也仍然需要确认，也不用什么词都从零发明。Schema.org 已经提供了很多常见对象和属性的词汇。FOAF 可以描述人和社交关系。Dublin Core 常用于描述文献资源及元数据，它们可以成为复用的起点。具体含义和使用范围还是要和自己的领域对得上。还有 DBpedia，按它的官方说明，它从 Wikipedia 里提取结构化信息，让这些知识可以被查询和复用。这里要记住这个方向，从 Wikipedia 提取知识形成 DBpedia，熟悉的词汇可以帮助我们起步，也要核对它原来的定义。假设这张图已经有了，接下来就问，系统能根据这些关系多知道一点什么。这里会用到 RDFS 和 OWL，前者提供基本的类别和属性语义。后者可以写出更丰富的本体公理，也就是具有明确逻辑含义的声明。先看一句话，Bob teaches Scooter，Bob 在教 Scooter，我们给 Teaches 这个关系做两个声明，它的 Domain（定义域）是 Teacher，它的 Range（值域）是 Student。Domain 可以先理解成关系左边的对象属于什么类别，Range 只是右边的对象属于什么类别。有了这条关系和声明，系统就可以推出 Bob 是 Teacher，Scooter 是 Student，如果我们还声明所有 Teacher 都属于 Person，那么 Bob 也是 Person，注意，后面这些类别信息未必是最开始主链路进去的，它们可以由已有事实和声明推导出来。这叫推理 Inference，它不是模型凭感觉觉得 Bob 像老师，而是根据定义推导得到一个结论。当然这个结论依赖我们的前提，如果 Teaches 的定义错了或者原始关系记错了，推导本身不会神奇地纠正那些前提。这里我补充一个容易混淆的区别，RDFS 的 Domain 和 Range 只会参与推出关系两端对象的类型。它们并不天然等于类型校验，预检不对就拒绝保存，如果我们希望检查眼前这批数据，发现不满足条件就返回失败，还需要相应的数据校验和处理逻辑。再看 OWL，全称是 Web Ontology Language，Web 本体语言，用祖先关系就能看见另一种推断，Sue 是 Mary 的祖先，Mary 是 Anna 的祖先。如果 Ancestor 被声明为传递属性，我们就可以推出 Sue 也是 Anna 的祖先。这一步的价值是系统可以根据关系的含义得到间接关系，我们不必把所有能够推出的关系都手动录一遍，不过前提很明确，这里声明的是祖先关系的传递性，不能看到图上有条路径，就把任何关系都照着传下去，所以看一张本体图，除了看谁和谁相联还得看每条关系声明了什么，我们能推出哪些结论要依据这些声明来判断，还有一个词叫 Functional Property，功能性属性，也有人叫函数属性，我们用父亲关系来看，它指向的是人，本文不具体讨论。功能对象属性，对同一个主体经由该属性，至多关联一个对象，函数在这里不止某一段程序代码，我们现在这个校验模型里把 hasFather 设为这样的关系，现在有两条记录，Jamin 的父亲是 Bob，Jamin 的父亲又写成 Bb，系统并不一定立即说出现两个名字，所以第二条错了，它可以推出 Bob 和 Bb 是同一个人的两个名称，这里再补充一个条件，OWL 不会仅仅因为名字不同，就默认它们代表不同对象，如果我们还明确声明 Bob 和 Bb 不是同一个人，那么这些信息与前面的功能性要求放在一起就会出现不一致，所以推理器得到一个结论，和业务程序拒绝一次操作是两个需要衔接的动作，我们可以用本体表达领域含义，进行推导或发现逻辑不一致，接着还要由系统决定，这个结果意味着通过、修正、停止还是交给人处理。这几种推断说清楚了，接下来把 Agent 放回来，Agent 要持续做事通常会反复经历一个循环，看当前信息决定下一步，调用相应能力拿到新结果再决定要不要继续，程序里的顺序、条件分支和循环都有很长的历史，循环让一次处理能够反复进行，Agent 也因此可以持续尝试，与此同时什么时候停下来就成了必须明确处理的问题，循环出问题不止一种情况，结果一直不对，程序可能还在反复重试，多个 Agent 互相传消息也可能越跑越偏，调用继续，时间和 token 消耗也继续，所以接了本体，人要处理停止条件和失败后的去向。接下来看，Claude 的客户端工具调用循环，先把模型和应用程序分开看，应用程序把任务、对话记录和可用工具的说明交给模型，模型根据这些信息提出要调用哪个工具以及参数应该是什么，比如模型返回一个结构化的调用建议，这里很重要，返回调用建议还不等于动作已经发生，对于这个客户端工具的例子，真正运行函数、访问相应系统的是应用程序，我们在这里就能安排检查，而不必等一个有副作用的动作做完以后才去评判它对不对，看代码的时候可以留意两个位置，一个是返回内容里的工具调用块，里面有工具名称和参数，另一个是 Stop Reason，也就是这次响应为什么停下来，当它是 tool_use 时，意味着当前响应要求使用工具，程序需要进入相应处理分支。接着程序提取调用内容和参数，再执行允许执行的工具，对，只读取数据、计算结果或者准备候选结果的工具，我们可以拿到结果以后继续检查。像真正修改数据库、发出付款这种动作，则要把必要的检查安排在提交之前，这些工具在流程里的位置不能只看一个函数名字来判断，这里就得分清副作用，这次运行是否真的改变了外部状态，你只是计算出一个拟议结果，和已经把数据改了是两种情况。前者还有机会检查，后者即使发现不对也可能需要额外补救。工具产生的信息还需要转成检查程序能理解的形式，比如明确它指的是哪个对象、哪条关系、哪一个状态，再与领域中已有的事实和声明放在一起看。不能只把一段自然语言原封不动交给另一个模型，说你帮我看看合理不合理，就宣称已经完成了本体推理。检查通过以后，流程才进入下一步，没有通过就把具体原因交回去，是哪个对象对不上，缺了哪项必要信息，还是某条规则与候选结果冲突。Coyle 提到可以把失败交回模型，也可以让人介入，落到程序里我们还要明确是否重试。重试几次，以及什么时候停止。模型收到工具结果或者失败原因，再生成下一步，循环才闭合。模型拿到的是这次检查的具体结果，再据此尝试，程序也保留停止它的控制，如果图上写着检查，实际却只是记录一条日志，照常执行，那这一层检查就没有发挥作用。具体做数据检查，可以看 Pydantic。它是 Python 中常用的数据验证工具，能根据定义好的数据模型检查输入，Python 是动态类型语言，变量可以先指向一个整数，后来再指向一段文字。对象仍有自己的类型，我们还要明确本次输入究竟需要什么？比如字段需要整数，数据需要哪些结构都可以写出要求。是否允许类型转换也要配置清楚，这里补充一点。Pydantic 还支持自定义断言和模型校验，有条件和无条件同样可以写进去。入口检查和领域检查是职责分工，工具的能力可以重叠。Coyle 用了一句很有记忆点的话，Pydantic checks at the door, and ontology checks at the ledger，我把它理解成这个示例里的两个检查位置。入口核对参数，准备把结果纳入业务状态的时候，再核对领域里的含义和关系。画面上把这两个位置标出来，比只背两个工具名更有用。从这个例子回到工程选择，还会遇到一个问题，既然规则可以写代码，为什么考虑本体？有些简单条件直接写校验代码就很好。本体值得考虑的地方是我们希望对象关系和含义能够被共同使用，并且希望依据这些进行一致性推导。它要进入现有的程序和数据系统才能发挥作用。最后看几个错误，用它们检验前面的解释。第一个是同一个订单又出现一笔退款。在这个例子里，先假定业务要求一张订单只能有一次退款。这是示例的政策设定，不能把它当成所有订单天然遵守的规则。我们前面刚讲过，功能对象属性可以带来同一性推导，它本身不会替支付系统执行拒绝。真的要挡住一次不符合规则的操作，还要让检查结果控制提交，并与实际系统中的约束配合。把这个连接补出来，才是在解释怎样避免错误。第二个例子是把钱付给客服，而不是这张订单的买家。Coyle 在示例里，把 Customer，也就是客户和 Support Rep，也就是客服代表声明为互斥类。这里讨论的是示例中的账户类别。要补清楚一个条件，如果同一个账户同时被归进这两类就会产生不一致。真的检查这次付款，还要核对付款对象和订单买家的关系，并让检查结果控制执行。日常可以理解成这个模型不允许同一个对象，同时属于这两类。原图使用的是类互斥，和两条属性本身互斥，含义不同。检查时，要把参与判断的类别、对象、事实和处理结果接起来。第三个例子是状态。在这个例子里，系统直接说 Paid、Shipped、Refunded 这几种状态。模型就给出 Probably Shipped，大概已经发货。人可以读懂这个猜测，但程序需要的是明确状态。要规定允许的取值，并让实际校验器检查。如果缺少发货事实也不能靠一句大概，把它补成已发货。这些例子各自说明一件事，有的要核对对象是不是同一个，有的要核对关系，有的要核对取值。共同的难点是把业务里的要求表达清楚，再让它真正参与程序的判断。自然语言很适合让人提出需求，也需要继续落实到系统可以处理的定义和检查上。Agent 和 Ontology 放在一起，可以让系统在提出下一步之后，根据领域知识继续核对。这一步依赖哪些事实，按照我们已经明确的关系和规则，结论是否成立。如果不成立应该把什么原因交回去，以后看一个 Agent 的方案，我会沿着这条运行路径找一遍。先看模型交出了什么，再看检查用了哪些事实和声明，最后看检查结果能不能真的影响动作。如果那一层只画了一个叫本体的框，输入、输出和失败分支都还没说清，方案就还有工作要做。本体帮助我们把共享的知识和含义表达出来，推理与校验帮助我们检查候选结果。程序把这些检查接入执行过程，这样对 Agent 能做什么，我们就有了一条可以追问也可以逐步核对的依据。
