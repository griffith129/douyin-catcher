## 一句话结论
AI 写代码不应靠多模型围着静态 diff 对抗互审，而应让具体功能走 TDD 与真实运行验证，让复杂架构与状态机走大模型辅助的形式化验证（TLA+ / Kani）。

## 核心要点
- 作者从一开始就反对大模型之间搞对抗性代码审查，认为让一个模型写完后拉几个模型对 diff 挑刺从根子上走偏。
- 对抗性审查脱离运行环境，模型算不清全局不变量，只能把看似风险全报上来，容易产生大量假警报。
- 为通过审查，写代码的 Agent 会塞防御性分支和冗余补丁，导致 token 多烧数倍、干净改动膨胀成难维护补丁。
- 审查模型盯着 diff 往往看不出真正一跑就崩的问题，如界面卡死和配置漏配。
- 正路一是 TDD 与真实运行验证：先写测试定预期、先跑红再写刚好跑绿的实现，并把真实程序拉起来点一遍。
- 正路二是用大模型做形式化验证：把复杂架构抽成状态机，交给 TLA+ 或 Kani 穷举执行顺序，并用故意改坏的模型跑红证明能抓死锁。

## 关键细节
- Lauren Tan 是 Rust 编译器核心成员、现于 xAI 做 Grok；其工程插件包 Pistachle 大幅砍掉对抗性代码审查，准备彻底删除。
- 对抗性审查的典型假警报包括担心缺空值判断、怀疑并发会乱序等，核对后发现十有八九是假警报。
- 代价例子：token 多烧好几倍；原本干净的十行改动膨胀成一百行没人敢碰的补丁。
- 真正漏掉的问题例子：界面卡死、配置漏配。
- TDD 流程：先写测试把预期行为定死，先看到测试跑红，再写刚好跑绿的实现；真实测试跑下去三秒见分晓。
- 形式化验证适合并发竞争、网络重连、多端同步等架构设计，错误常在几十步交错的死角里；先故意改坏模型并跑红一次，证明验证能抓出死锁。
- 质量机制两个硬指标：真实发生过的线上故障放回去能否 100% 拦住；每拦住一个真问题要陪它处理多少假警报。
- 重复犯过两次的错按从硬到软顺序固化到底座里，原文提到类型系统、TDD 测试等层级（部分语音识别不清）。
