# 功能扩展方案对比（2026-11-10）

> 前提：MVP 基线已固化（tag `v0.1.0-mvp`，80 测试全绿）。所有扩展遵循：
> ① 新功能全部 TDD；② 不修改 MVP 核心路径函数签名；③ Notion 写入失败自动降级本地（现有机制）；④ 每个 feature 独立分支，合并前跑全量测试。

## 功能 1：Notion 笔记分类检索（快速找到某类/某个视频）

| 方案 | 思路 | 优点 | 缺点 | 实施成本 | 维护成本 |
|---|---|---|---|---|---|
| 1A. Notion Database 化 | 视频库（每视频一行，title/作者/分类/日期/链接为 property，正文为行内子页面） | Notion 原生筛选/排序/搜索全可用；是功能 2、3 的最佳地基 | 需迁移现有已传笔记（或新旧并存）；行内页面 UI 与普通子页略不同 | 中（建库+改 upload_note 为 upsert 行+迁移脚本） | 低 |
| 1B. 分类页面树 | 按大类建子页面，视频页挂在对应大类下 | 实现最简单（改 parent 即可）；直观 | 跨类检索弱；改分类=移动页面；多主题视频只能归一类 | 低 | 中（树会长乱） |
| 1C. 本地索引+选择台检索 | Notion 保持平铺；本地 SQLite/JSON 索引，:8787 加"笔记库"搜索页，跳转 Notion URL | 零迁移、MVP 零风险；本地检索能力最强 | 检索体验在本地不在 Notion | 低-中 | 低 |
| 1D. 双库+Relation | 视频库 + 分类库，relation 关联，rollup 统计 | Notion 内最规范；分类页自动聚合视频；新增大类=插一行 | schema 设计+relation 写入最复杂；需适应 database UI | 高 | 低 |
| 1E. 混合：1A+1C | Notion database 供人工浏览 + 本地索引供选择台快速检索/批量操作 | 两边体验都最优；本地索引可反哺选择台"已处理"状态 | 双写一致性需同函数内先后写+可重放；实施量最大 | 中-高 | 低 |

## 功能 2：更新查看（本次更新集合 + 历史按分类浏览）

| 方案 | 思路 | 优点 | 缺点 | 实施成本 | 维护成本 |
|---|---|---|---|---|---|
| 2A. 批次 property+筛选视图 | pipeline 打 batch_id/updated_at，Notion database 按批次筛选；本次更新=一个视图 | 依赖 F1 选 database；批次可长期回看 | 视图需手动建或经 MCP 建；单独看"最近一批"要点一下筛选 | 低（若 F1 已 database 化） | 低 |
| 2B. 本地批次报告页 | :8787 每次批量后生成"本次更新"报告（标题/分类/Notion 链接），可回看历史批次 | 与选择台工作流天然衔接；零 Notion 依赖；即时可见 | 要开本地页看 | 低 | 低 |
| 2C. Notion 更新日志页 | 每次批量在 parent 下写一篇"更新日志 YYYY-MM-DD"，内含本次视频链接列表 | 纯 Notion 内；复用现有 upload_note；历史批次天然是列表 | 日志页会堆积（比视频少 2 个数量级）；跳转一层 | 低 | 低 |
| 2D. 本地时间线+分类导航 | 本地"更新"页（时间线）+"分类"页（树形），读本地索引 | 交互自由度最大；集中一处 | 全在本地，不在 Notion | 中 | 低 |
| 2E. 分类页顶部"最近更新"区块 | 每个大类子页面头部维护最近更新列表 | 进入分类即见最新 | API 维护头部 blocks 繁琐、一致性差 | 高 | 高 |

## 功能 3：LLM 自动分类（大类→细类，新视频自动归类/建新类）

| 方案 | 思路 | 优点 | 缺点 | 实施成本 | 维护成本 |
|---|---|---|---|---|---|
| 3A. 无状态 prompt 分类 | 每次把现有大类清单塞 prompt，LLM 输出大类+细类，可自由创新类 | 实现最简单、零存储 | 清单变长 prompt 变大；LLM 命名不稳定（"Agent开发"vs"AI Agent"漂移） | 低 | 中 |
| 3B. 分类清单持久化+受限选择 | categories.json 为 source of truth；LLM 只能从清单选或返回 proposal，经相似度去重后入库 | 命名稳定可控；可人工调整清单；prompt 稳定 | 多一层状态管理 | 中 | 低 |
| 3C. 两级 LLM 调用 | 第一次定大类，第二次在大类内定细类 | 每次 prompt 小；分步可验证 | 调用与延迟翻倍；总成本高 | 中 | 中 |
| 3D. Embedding 相似度+LLM 兜底 | 分类建描述向量，新视频先比相似度，低于阈值才 LLM 创新类 | LLM 调用最省 | 需 embedding API（本地反代支持性未验证）或本地模型；复杂度最高 | 高 | 中 |
| 3E. 关键词规则预分类+LLM 兜底 | 规则表快筛，未命中才 LLM | 省 token 省 时延 | 规则长期维护负担；与"LLM 自动化"初衷相悖 | 低 | 高 |
| 3F. 混合（3B+Notion property 联动） | 3B 为核心，分类结果写 Notion database select property，新大类自动插入新 option | 与 F1 database 方案无缝；Notion 侧筛选即分类视图 | 依赖 F1 database 化 | 中 | 低 |

## 组合建议（供参考，最终由用户定）

- **倾向 Notion 为唯一浏览入口**：1A 或 1D + 2A/2C + 3F
- **倾向选择台为工作中心、Notion 为归档**：1E（或 1C）+ 2B+2C 双保险 + 3B
- **最小改动快速见效**：1B + 2C + 3A，后续再升级 database

## 待确认决策点

1. 一个视频是否允许属于多个大类？（单选 vs 多选，影响 property 设计与 prompt 输出格式）
2. 分类浏览的主入口放在 Notion 内、本地选择台，还是两边都要？
3. 现有已上传的 N 篇笔记是否需要迁移进新结构（还是从某个时间点起新结构生效）？
