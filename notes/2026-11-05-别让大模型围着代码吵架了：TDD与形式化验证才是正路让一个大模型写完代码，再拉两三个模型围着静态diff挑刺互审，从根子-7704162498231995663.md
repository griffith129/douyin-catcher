## 一句话结论
不要用多个大模型围着静态 diff 做对抗性互审来代替真实运行验证；AI 写代码应走 TDD/真实运行与形式化验证两条正路。

## 核心要点
- 作者反对让大模型写完代码后，再拉多个模型脱离运行环境对静态 diff 挑刺互审。
- 对抗性审查无法像编译器一样算清全局不变式，也没有真正运行程序，容易产生假警报和过度设计。
- 这种互审会诱导写代码的模型堆防御性分支和冗余兜底，导致 token 浪费、干净改动膨胀。
- 真正一跑就崩的界面卡死、配置漏配等问题，静态 diff 互审往往看不出来。
- 具体功能实现应靠 TDD：先写测试跑红，再写刚好跑绿的实现，并真实运行验证。
- 复杂架构与状态机应让大模型抽取状态机，交给 TLA+ / Kani 穷举验证，形成数学兜底。

## 关键细节
- React 编译器核心成员 Lauren Tan 发推文提到，其工程插件包 Pstack 大幅砍掉对抗性代码审查，并准备彻底删掉。
- 对抗性审查常纠结命名细节或编造过度设计，并担心空值判断、并发乱序等，但核对后十有八九是假警报。
- 原本干净的十行改动，可能在几轮互审后膨胀成一百行没人敢碰的补丁。
- TDD 与真实运行可让很多边界争论“一行真实测试跑下去，三秒钟就见分晓”。
- 形式化验证可用 TLA+ 和 Kani 穷举状态；在故意改坏的模型上跑红一次，可证明它真能抓出死锁。
- 重复犯过两次的错，按从硬到软顺序焊死在底座：单一状态源、类型系统让非法状态编译不过、TDD 测试、文档。
- 衡量质量机制有两个硬指标：真实线上故障放回去能否 100% 拦住；每拦住一个真问题要陪它处理多少假警报。

## 原文文案

我从一开始就反对让大模型之间搞对抗性代码审查，AI 写代码只有两条正路。具体功能的实现靠 TDD 测试驱动开发和真实运行验证，架构与复杂状态机的设计，现在大模型可以做形式化验证。对，也是正路。让一个大模型写完代码，再拉两三个大模型对着 diff 挑刺，从根子上就是走偏了。前两天，React 编译器核心成员 Lauren Tan 发了条推文，说的正是这件事。她的工程插件包 Pstack 里大幅砍掉了对抗性代码审查，准备彻底删掉，因为让 AI 脱离运行环境，对着静态代码空谈审查，只会扎进吹毛求疵的命名细节或者编造一堆过度设计。为什么对抗性审查会失灵？因为大模型没法像编译器那样算清全局不变式，也没把程序真跑起来看一眼，只能顺着字面意思猜。为了交差，他把所有看起来像风险的地方全报上来。一会儿担心缺个空值判断，一会儿怀疑并发会乱序，去核对就会发现十有八九是假警报。更要命的是，写代码的 AI，为了过关，会往代码里塞满防御性分支和冗余兜底，几个回合下来，token 多烧了，原本干净的十行改动膨胀成一百行没人敢碰的补丁。而真正一跑就会崩的界面卡死、配置漏配，几个审查模型盯着 diff 看了半天，一个也没看出来。互审吵架的 token 省下来，回到两条正路上，这笔账才算得过来。第一条正路是 TDD 与真实运行，先写测试把预期行为定死，先看到测试跑红，再写刚好跑绿的实现，把真实程序拉起来，点一遍，看一眼。很多争论不休的边界问题，一行真实测试跑下去，三秒钟就见分晓。第二条正路是用大模型做形式化验证，并发竞争、网络重连、多端同步这些架构设计，出错往往在几十步交错的死角里。现在大模型非常适合把架构抽成状态机，交给 TLA+ 和 Kani 去穷举所有状态，只要在故意改坏的模型上跑红一次，证明它真能抓出死锁，以后每次改架构就都有了数学兜底。凡是重复犯过两次的错，就按从硬到软的顺序，焊死在底座里，先合成单一状态源，再用类型系统让非法状态编译不过，接着写进 TDD 测试，最后才写进文档。衡量一套质量机制有两个硬指标，第一，把真实发生过的线上故障放回去能不能百分之百拦住。第二，每拦住一个真问题要陪它处理多少个假警报，靠大模型嘴皮的互审，这两个指标永远算不过账，只有 TDD 加形式化验证才是经得起检验的正路。谢谢大家，我们下期见。
